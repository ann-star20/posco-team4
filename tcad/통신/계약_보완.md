# 모델 서비스 연결 계약(fab-ml-v1) 보완 사항

계약 문서에 적힌 것과 **우리 모델의 실제 값이 다른 곳**, 그리고 계약에 **추가가 필요한 것**을 근거와 함께 정리했다. 확인한 방법은 TCAD 실행 기록(`대량작업2/대량실행/runs/001/실행기록.log`), deck(`최종_trench_template.in`), 코드를 직접 읽은 것이다.

## 1. 계약 문서를 고쳐야 하는 것 (근거 확인됨)

| 항목 | 계약 문서의 예시 | 실제 | 근거 |
|---|---|---|---|
| `id_conditions.vds_v` | 1.0 | **0.1** | deck `solve vdrain=0.1`, 실행 기록 `V(drain) = 0.1`, Id 는 게이트 0→4 V 스윕의 4.0 V 점 (`단계시험.py parse_iv`) |
| `id_conditions.vgs_v` | 4.0 | 4.0 (맞음) | deck `solve vgate=0.0 vstep=0.1 vfinal=4.0` |
| `id_conditions.temperature_c` | 25.0 | **26.85** (300 K) | Atlas 로그 `Temperature = 300 K` |
| 입력 예시 값 | body_dose 1.2e13, epi_doping 2.5e15, oxide_thickness 5.2 | 기준값 **7.7e12, 1.7e16, 0.06** (이 근처 ±30 % 범위가 학습 영역) | `단계시험.py BASE`, 실행 기록 `set DOSE = 7.7e+12` 등. 예시 값은 영역 밖이라 서비스가 OUT_OF_DOMAIN 으로 거절한다 |
| 산화막 단위 | (미표기, 예시 5.2) | **μm** (0.06 = 60 nm) | 실행 기록 `deposit oxide thick=0.06`, `Dimensions in microns` |
| 전류와 gm 단위 | (미표기, 예시 gm 11.42, id_on 37.8) | 폭 **1 μm 당** 값. 서비스는 gm **μS/μm**, id_on **μA/μm** 로 응답 | 실행 기록 전극 전류 단위 `Jn(A/um)` |

## 2. 확인했지만 완전히 증명하지는 못한 것
| 항목 | 상태 |
|---|---|
| 도즈 cm⁻², 에피 cm⁻³ | **확인됨.** deck: `implant boron dose=$DOSE`, `init silicon c.phos=$N_DRIFT` (실행 기록 `implant boron dose=7.7e+012`, `init silicon c.phos=1.7e+016`). 사용자 PC 의 Silvaco 자료 "Process simulation - Silvaco" 20쪽 "Implant dose (in atm/cm2)", 13쪽 "Concentration in atom/cm3", 16쪽 산화막 µm. 공식 매뉴얼 원문은 아니고 이 자료로 확인했다 |
| 이상 판정 스펙 (Vth 1.7~2.6 V, BV 40 V 이상) | 기준 소자 **AOI4184 데이터시트**(VGS(th) 최소 1.7/최대 2.6 V, BVDSS 최소 40 V)와 같은 값. 응답 `metadata.spec.status` 는 `datasheet_AOI4184`. 데이터시트 Vth 는 ID=250 µA 정의라 TCAD Vth 추출 방식과 같은지는 미확인 |
| gm, id_on 의 합격 범위 | **정하지 않기로 결정 (사용자 결정).** 합격·불량 판정은 Vth, BV 만 쓰고, gm 과 id_on 은 원인 진단 신호로만 쓴다. 근거: 데이터시트에 대응 규격이 없고(gFS 는 Vds=5 V 소자 전체 값), id_on 은 Vth 와 상관 −0.95 라 따로 범위를 걸어도 새 정보가 없다 |
| 소자 폭 | 정해지지 않았다. 데이터시트(RDS(on), gFS)는 소자 전체 기준이고 우리 값은 µm 당이라 절대값 비교 불가. 폭을 곱해 절대 A, S 로 바꾸는 요구가 있으면 폭을 먼저 정해야 한다 |

## 3. 계약에 추가한 것
- **`task_type: "diagnose"`**: 측정값 → 원인, 보정안, 다음 측정 권고. 요청 `input_payload.measurements`(vth V, gm μS/μm, id_on μA/μm, bv V 또는 null), `n_wafers`, `refine`. 응답 `result_payload`(decision, knobs, next_measurement, compensation, fit, refine, spec)와 `tcad_proposal`. 자세한 예는 `예시/3_diagnose_산화막+15퍼센트_apply.json`
- **surrogate 응답의 `metadata.sigma`, `metadata.in_domain`, `metadata.spec`**
- **오류 코드** (Gateway 요청서의 이름): `OUT_OF_DOMAIN`(HTTP 200, status failed), `INVALID_INPUT`(400; JSON 오류, 필드 오류, 알 수 없는 schema_version 포함), `UNSUPPORTED_CONTRACT_VERSION`, `UNSUPPORTED_TASK_TYPE`, `MODEL_NOT_READY`(진단 모델 로딩 실패), `UNAUTHORIZED`(401), `INFERENCE_FAILED`(500; 예기치 못한 내부 오류). `TIMEOUT`, `RESOURCE_EXHAUSTED` 는 아직 서비스가 내지 않는다. 실패 응답에는 최상위 `error_code`·`error_message`, `result_payload: null`, `tcad_proposal: null` 과 `metadata.model/timing_ms/stages` 가 들어간다.
- **보정 경로 (`compensation.route`)**: 에이전트가 보정값을 TCAD 없이 적용해도 되는지 임계값으로 정한다.
  | route | 의미 | tcad_proposal |
  |---|---|---|
  | `apply` | 임계값 5개를 **모두 통과**: 보정 후 Vth·BV 규격 안 확률 ≥ 0.99, 원인 확률 ≥ 0.90, 보정량 ≤ ±15 %, 에피 이탈 확률 ≤ 0.05(에피는 보정 불가), 보정 후 모든 변수가 0.70~1.30. **TCAD 검증을 건너뛰고** 보정값(`target_process_parameters`)을 적용하는 후보 | null |
  | `tcad_verify` | 임계값을 **하나라도 못 채움**. 사유는 `confidence_blockers` (`CAUSE_NOT_CONFIDENT`, `EPI_DEVIATED_NOT_CONTROLLABLE`, `SPEC_NOT_ASSURED_AFTER`, `CHANGE_TOO_LARGE`, `OUT_OF_CORE`). TCAD 로 검증 | 필수 (후보마다 `predicted_outputs`) |
  | `no_action` | 정상으로 판정, 보정 불필요 | null |
  | `manual` | `POOR_FIT` (학습하지 않은 유형), 사람이 판단 | null |
  - `compensation.target_process_parameters`(보정 후 목표 공정값), `target_predicted_outputs`(그 공정값에서 서로게이트가 예측한 특성)는 `apply`, `tcad_verify` 둘 다 들어간다.
  - `high_confidence`(true/false), `confidence`, `threshold_evidence`, `thresholds`(사용한 임계값, 상태 provisional)도 응답에 들어간다.
  - `requires_human_approval` 는 `apply`/`tcad_verify`/`manual` 에서는 항상 true (`apply` 도 TCAD 만 건너뛸 뿐 관리자 승인은 별개 절차, Gateway 정책). **`no_action`(정상)은 예외로 false** — 승인할 대상이 없어서다. 아래 3-1 참고.
  - 스위치: `변환기.py` 의 `SKIP_TCAD_WHEN_HIGH_CONFIDENCE` 를 False 로 하면 보정 후보가 전부 `tcad_verify` (팀 정책이 TCAD 필수로 정해지면 이것만 바꾼다).
  - 임계값은 **임시 기준**이다 (`변환기.py` 의 `AUTO`). 실제 TCAD 불량 샘플 96개와 기준값 근처 소이탈 샘플 36개로 평가했을 때 apply 후보의 오판은 이웃 TCAD 샘플 기준으로 0~1건이었지만 건수가 적어(N=100에서 7건) 오판율을 확정하지 못했다 (`진단에이전트/결과/소이탈평가.md`).
- **`POOR_FIT` 경고** (diagnose): 측정값이 학습 영역의 어떤 상태와도 잘 맞지 않을 때. 이때 `decided: false`, `tcad_proposal: null`
- **정상(no_action)일 때 보정탐색 생략, 검사결과 DB 기록 (2026-10-22 추가)**: `통신/모델서비스.py` `_diagnose()`.
  - 1단계(`agent.diagnose`: 격자 탐색·사후분포, 노브별 판정)는 **항상 돌린다.** 이게 "노브가 정상인지"를 확인하는 유일한 방법이기 때문이다 — 측정값만으로는 부족하다: 예를 들어 에피가 30% 벗어나도 BV 를 안 재면 Vth 만으로는 스펙 안으로 보일 수 있고, 이 경우 `판정됨=false`(구분 불가)가 나와야 정상이다. 그래서 `violates_spec`(측정값 vs 스펙) 만으로 건너뛰는 건 **쓰지 않는다** — 이 방식은 위 에피 사례를 "정상"으로 잘못 기록하는 구멍이 있어서 폐기했다.
  - 1단계 결과가 **`판정됨(decided)=true` 이고 `최다범주=정상` 이고 `poor_fit` 도 아닐 때만**, 비용이 큰 2단계(`recommend`: 다음측정 시뮬레이션, `compensate`: 도즈·산화막 21×21 격자 탐색 — 정상 케이스 기준 전체 처리시간의 90% 이상)를 **생략한다.**
  - 이때 응답은 `result_payload.decision`·`knobs`·`fit` 은 그대로 채워지고(판정에 쓴 값이라 공짜로 나온다), `next_measurement` 는 **`null`**, `compensation` 은 `{"route": "no_action", "requires_human_approval": false, ...}` 만(보정안 관련 필드 없음).
  - `metadata.timing_ms.compensation_search` 가 0에 가깝다(이전엔 정상이어도 ~2초 걸렸다. `diagnosis` 단계(격자 탐색)는 그대로 돌아 ~100ms 든다).
  - 이 경로일 때만 측정값(vth, gm, id_on, bv)과 `request_id`, `n_wafers` 를 `INSPECTION_DB`(기본 `통신/검사결과.db`, SQLite, 환경변수로 경로 변경 가능)의 `inspections` 테이블에 적재한다. **이 DB는 임시 기록용**이고, 운영 DB(승인 이력 포함)는 Gateway 가 따로 가진다.
- **재시도 안전**: 같은 `request_id` 는 같은 응답
- **선택 토큰**: `--token` 또는 환경변수 `FAB_SERVICE_TOKEN` 을 쓰면 헤더 `X-Fab-Token` 이 같아야 한다 (ASCII 토큰만)

## 4. 소요 시간 (이 PC, CPU)
| 작업 | 시간 |
|---|---|
| surrogate | 1~2 ms |
| diagnose (BV 없음, 넓은 사후분포) | 약 3~5 초 |
| diagnose (BV 측정, 웨이퍼 많음, 사후분포가 좁음) | 약 3~14 초 (좁은 영역을 촘촘히 다시 계산하는 시간) |
| diagnose + `refine: true` | 위에 10~18 초 더 (고정밀, 쓸 수 있을 때) |

**Jetson 실측(Python 3.10, NumPy 2.2.6, aarch64 6코어): surrogate HTTP 응답 6 ms, 진단(산화막 +15 %, BV 측정, 25장)이 3.5~3.8 초**로 이 PC(2.7~4.4 초)와 비슷했다. 다른 조건(사후분포가 좁은 경우 등)과 고정밀 포함 시간은 아직 재지 못했다. **Worker 의 diagnose 요청 제한 시간은 60 초 이상**으로 잡고, Jetson 에서 실제 시간을 측정해 조정할 것.

## 5. Gateway 요청서 반영 (2026-10-21)
- **경로**: `POST /api/v1/predict`(surrogate, diagnose/diagnosis 모두), `POST /api/v1/diagnose`(task_type 생략 가능), `GET /health/ready`(모델 목록, 해시, 로딩 시간), `GET /health`.
- **task_type**: 요청서의 `diagnosis` 와 처음 구현의 `diagnose` 를 둘 다 받는다.
- **분류 코드**: `top_category`, `category_probabilities` 키, `candidates[].category` 는 영문(`normal`, `dose`, `epi`, `oxide`, `dose+epi`, `dose+oxide`, `epi+oxide`, `dose+epi+oxide`), 한글은 `*_label`.
- **다음 측정**: `recommendation_code`(`none_needed`, `no_improvement`, `measure_bv`, `more_wafers_2x`, `more_wafers_4x`), `recommendation_label`, `actions[].action_code/action_label`.
- **보정**: `compensation.route` 는 `apply`/`tcad_verify`/`no_action`/`manual`, `requires_human_approval` 는 `no_action` 만 false 고 나머지는 항상 true, 임계값 판정 정보는 위 3번 항목. `tcad_proposal` 은 항상 필드가 있고 `tcad_verify` 일 때만 값이 있다.
- **메타데이터**: `metadata.model`(name, version, artifact_hash, training_data_version, git_commit, runtime, device, precision), `metadata.timing_ms`, `metadata.stages`. 시간은 ms, 단조 시계(`perf_counter`).
  - `artifact_hash` 는 서로게이트 모델 파일 4개(gp.npz, 영역.json, 모델정보.json, 학습배열.npz)를 묶은 SHA-256, `training_data_version` 은 학습 배열 파일 해시 앞 12자리다. **`git_commit` 은 저장소가 없어 null** 이다.
  - 서로게이트의 `stage1_vth_gm`, `stage2_id_on`, `bv_prediction` 은 모델이 한 번의 호출로 계산해서 **나누어 재지 않았다** (대신 `inference_total`). 진단은 `diagnosis`, `compensation_search`, `refine` 을 단계별로 잰다.
- **요청서와 다르게 둔 것**: `id_conditions.temperature_c` 는 요청서 예시 25.0 이 아니라 TCAD 실행 기록의 **26.85 (300 K)**. 요청서 예시 숫자(body_dose 3.2e13 등)는 학습 영역 밖이라 OUT_OF_DOMAIN 으로 거절된다 (시험에 넣음). 요청서의 동시 요청 수, 평균·최대 추론시간, 메모리 사용량 항목은 아직 재지 않았다.
