# 유니티 시연용 데이터 (Jetson·TCAD 서버가 모두 연결됐다고 가정)

전체 흐름은 `Gateway_연동_정리.md` 6절 구조를 따른다.
```
Unity ─WebSocket─▶ Gateway ─ROS 2─▶ Jetson Worker ─HTTP─▶ 모델 서비스 (Jetson)
                      │
                      └─HTTP─▶ TCAD 서비스 (워크스테이션 PC)
```

시연에서 보여줄 4가지 경로(`compensation.route`)를 모두 준비했다. ①②④는 Jetson 실기(`192.168.10.253`, `fabrx-model`)에 실제로 요청해서 받은 응답이고, ③은 TCAD 실제 계산으로 진행 중이다.

| # | 시나리오 | 파일 | route | 확인 상태 |
|---|---|---|---|---|
| 1 | 정상 (이상 없음) | `5_diagnose_정상_no_action.json` | `no_action` | **Jetson 실기 확인**, `학습데이터_최종.csv` B001(기준값) 과 동일 |
| 2 | 산화막 +15%, 보정 후 임계값 5개 모두 통과 | `3_diagnose_산화막+15퍼센트_apply.json` | `apply` (TCAD 생략) | 모델 직접 호출 예시. **특정 TCAD 학습 포인트와 연결되지 않음** (apply 가 걸리는 보정량 ≤15% 구간이 좁아서, 학습셋의 0.1 단위 단일노브 스윕에는 걸리는 점이 없었다) |
| 3 | 산화막 +25%, 보정량이 15% 넘어 TCAD 재검증 | `4_diagnose_산화막+25퍼센트_보정량큼.json` + `7_tcad_verify_요청_전체흐름.json` | `tcad_verify` | **완료.** 실제 TCAD 결과: vth 2.2299V, bv 41.808V (둘 다 규격 통과), 예측 대비 오차 0.06% 수준. IV 302초 + BV 931초 (약 20.5분) |

| 7 | 도즈 단일노브 -70% (학습 영역 밖) | `10_diagnose_dose단일노브-70퍼_POOR_FIT_manual.json` | `manual` | **Jetson 실기 확인**, S_dose_0.3 (팀이 `외삽시험용=Y` 로 직접 표시한 포인트) |

## CSV(`unity_test_samples.csv`) 점검 결과
처음엔 `normal_01`, `problem_01` 2행만 있어서 **이상 없음(no_action)과 TCAD 재검증(tcad_verify, 산화막 원인) 두 경로만** 보여줬다. 이건 프로젝트가 강조하는 세 가지를 다 보여주지 못한다:
1. 원인이 산화막 하나만이 아니라 **도즈·에피 중 어느 쪽이든** 확률로 추정한다는 것 (`dose_01`, `epi_01` 추가)
2. 확신이 높고 보정량이 작으면 **TCAD 없이 바로 보정**(`apply`)한다는 것 (`apply_01` 추가)
3. **에피는 레시피로 못 고친다**는 것 (`epi_01`의 경고 필드)
4. 학습 영역을 벗어나면 모델이 **판단을 보류**(`manual`/POOR_FIT)한다는 것 (`poorfit_01` 추가)

지금은 7행으로 `no_action`·`apply`·`tcad_verify`(산화막/도즈/에피 3가지 원인)·`manual` 을 모두 보여준다. `dose_01`·`epi_01`·`poorfit_01` 은 `학습데이터_최종.csv`의 실제 TCAD 라벨 포인트(S_dose_1.3, S_epi_1.3, S_dose_0.3)를 그대로 Jetson에 요청한 결과라 공정값(body_dose 등) 열도 믿을 수 있는 숫자다. 반대로 `apply_01`은 그 폭이 좁은 구간(보정량 15% 이내)에 걸리는 학습 포인트가 없어서 공정값 3열을 비워뒀다 — 거꾸로 숫자를 지어 넣지 않았다.

참고로 서로게이트 단독 호출 예시(`1_surrogate_기준값.json`, `2_surrogate_영역밖_계약예시숫자.json`)와 측정값 입력표(`unity_test_samples.csv`)는 기존 자료를 그대로 쓴다.

## Unity 화면에 매핑할 핵심 필드
- 측정 입력: `input_payload.measurements` (Vth, gm, Id, BV), `n_wafers`
- 판정: `decision.top_category_label`(원인), `decision.top_probability`(확신도), `decision.decided`
- 보정안: `compensation.route`, `compensation.target_process_parameters`, `compensation.target_predicted_outputs`
- 승인 대기 표시: `compensation.requires_human_approval` (항상 true — 시연에서도 "엔지니어 승인" 버튼을 거치는 것을 보여줄 것)
- `tcad_verify`일 때만: `tcad_proposal.candidates[]`, 그리고 TCAD 완료 후 `prediction_error`(예측 대비 실측 차이)와 Gateway의 규격 판정(Vth 1.7~2.6V, BV 40V 이상)

## 시연 순서 제안
1. **정상 케이스**(#1) 먼저 보여줘서 "이상 없으면 그대로 둔다"를 설명.
2. **apply 케이스**(#2)로 "확신이 높고 보정량도 작으면 TCAD 없이 바로 보정안을 제시"를 설명. 그래도 `requires_human_approval`로 승인 절차는 거친다.
3. **tcad_verify 케이스**(#3)로 "보정량이 크면(15% 초과) TCAD로 한 번 더 검증한다"는 전체 흐름을 보여준다. 접수(202, `queued`) → 진행(`running`) → 완료(`succeeded`) → Gateway가 규격 판정 → 승인 대기까지 순서대로. 실제로는 20~30분 걸리므로 시연에서는 "접수"와 "완료 후 화면"만 보여주고 중간은 스킵하거나 빨리 돌려서 보여주는 편을 권장.
4. **manual 케이스**(#4)로 "학습 영역 밖이면 모델이 판단을 보류하고 사람에게 넘긴다"를 설명.

## 남은 것
- `unity_test_samples.csv` 의 body_dose/epi_doping/oxide_thickness(공정값) 열은 problem_01처럼 **특정 TCAD 런과 연결된 값만** 믿을 수 있는 숫자다. apply/tcad_verify/manual 시나리오의 측정값은 진단 입력으로 직접 만든 예시라, 거꾸로 추정한 "공정값"을 CSV에 끼워 넣으면 실제로 그 공정에서 나온 값처럼 보여 오해를 줄 수 있어 넣지 않았다. 필요하면 해당 측정값을 내는 공정값을 TCAD로 거꾸로 찾아서(= 역방향 런) 채워야 한다.
