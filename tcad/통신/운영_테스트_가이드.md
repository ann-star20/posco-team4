# 서로게이트·진단 모델 서비스: 동작 과정, 테스트, Jetson 운영 가이드

계약 fab-ml-v1, 서비스 버전 1.1.0. 이 문서는 (A) 전체 동작 과정과 요청·응답, (B) 테스트 순서, (C) Jetson 서버를 껐다 켤 때의 구동·확인 방법을 한곳에 정리한다.

표시: **[확인됨]** = 실제로 실행해서 확인한 것, **[표준 명령]** = 일반적인 리눅스 명령이라 Jetson에서 처음 쓸 때 결과를 확인할 것.

---

# A. 전체 동작 과정과 요청·응답

## A-1. 누가 무엇을 하나

```
Unity ──WebSocket──▶ Gateway ──ROS 2──▶ Jetson Worker ──HTTP──▶ 모델 서비스 (Jetson 127.0.0.1:8300)
                        │                                              │
                        │◀───────── 응답 (예측/진단 + route) ◀──────────┘
                        │
                        └─ route 가 tcad_verify 면 ──HTTP──▶ TCAD 워크스테이션 (Silvaco)
                                                              (이 서비스는 아직 없음)
```

| 구성 | 하는 일 |
|---|---|
| 모델 서비스 | 공정값 → 특성 예측(surrogate), 측정값 → 원인·보정안 진단(diagnose). TCAD를 호출하지 않는다 |
| Worker | 모델 서비스에 HTTP 요청을 보내고 결과를 ROS 2로 전달 |
| Gateway | 결과 저장, `route`를 보고 TCAD 검증 요청, 관리자 승인, Unity에 결과 전송 |
| TCAD 워크스테이션 | 보정 후보를 Silvaco로 계산해 검증. 현재는 스크립트(`대량실행.py`)만 있고 HTTP 서비스는 없음 |

## A-2. 엔드포인트

| 메서드·경로 | 용도 |
|---|---|
| `GET /health` | 서비스 상태, 계약 버전, 스펙 |
| `GET /health/ready` | 준비 완료 점검(모델 목록, 해시, 로딩 시간) |
| `POST /api/v1/predict` | `task_type`이 `surrogate` 또는 `diagnose`/`diagnosis` |
| `POST /api/v1/diagnose` | 진단 전용 (`task_type` 생략 가능) |

토큰을 쓰는 경우 요청 헤더에 `X-Fab-Token: 영문토큰`을 넣는다 (`/health`는 토큰 없이 열림).

## A-3. 시나리오 1: 서로게이트 (공정값 → 특성)

요청:
```json
{"schema_version": 1, "task_type": "surrogate", "request_id": "t-001", "job_id": "job-1", "run_id": "run-1", "attempt": 1,
 "model_contract_version": "fab-ml-v1", "surrogate_mode": "prod",
 "input_payload": {"process_parameters": {"body_dose": 7.7e12, "epi_doping": 1.7e16, "oxide_thickness": 0.06},
                   "requested_outputs": ["vth", "gm", "id_on", "bv"]}}
```
단위: `body_dose` cm⁻², `epi_doping` cm⁻³, `oxide_thickness` µm.

응답 (핵심만, 기준값 예시) **[확인됨]**:
```json
{"status": "succeeded", "request_id": "t-001", "anomaly_detected": false,
 "result_payload": {"vth": 2.26, "gm": 4.599, "id_on": 5.207, "bv": 41.115},
 "metadata": {"in_domain": true, "sigma": {"vth": 0.0014, "gm": 0.027, "id_on": 0.0043, "bv": 0.0100},
              "id_conditions": {"vgs_v": 4.0, "vds_v": 0.1, "temperature_c": 26.85},
              "units": {"vth": "V", "gm": "uS/um", "id_on": "uA/um", "bv": "V"},
              "model": {"name": "mosfet-gp-surrogate", "version": "2026-10-18", "artifact_hash": "sha256:…"},
              "timing_ms": {"inference_total": 0.9, "service_total": 3.0}},
 "tcad_proposal": null}
```

실패 응답 (학습 범위 밖) **[확인됨]**: HTTP 200, `status: "failed"`, `error_code: "OUT_OF_DOMAIN"`, `result_payload: null`. 단위를 잘못 보내도(예: 요청서 예시 숫자 3.2e13, 1.0e16, 0.05) 여기서 걸린다.

## A-4. 시나리오 2: 진단 (측정값 → 원인, 보정안)

요청:
```json
{"schema_version": 1, "task_type": "diagnosis", "request_id": "d-001", "job_id": "job-2", "run_id": "run-1", "attempt": 1,
 "model_contract_version": "fab-ml-v1", "surrogate_mode": "prod",
 "input_payload": {"measurements": {"vth": 2.874, "gm": 3.767, "id_on": 3.468, "bv": 44.186},
                   "n_wafers": 25, "refine": false}}
```
`bv`를 측정하지 못했으면 필드를 빼지 말고 `null`로 보낸다. `n_wafers`는 측정값이 몇 장의 평균인지(많을수록 판정이 확실해진다).

응답 (산화막이 +25 % 두꺼워진 예, 핵심만, 값은 `예시/4_diagnose_산화막+25퍼센트_보정량큼.json`의 실제 응답) **[확인됨]**:
```json
{"status": "succeeded", "anomaly_detected": true,
 "result_payload": {
   "decision": {"decided": true, "top_category": "oxide", "top_category_label": "산화막", "top_probability": 0.948,
                "category_probabilities": {"normal": 0.0, "dose": 0.0, "epi": 0.0, "oxide": 0.948, "dose+oxide": 0.052, "…": 0.0}},
   "knobs": {"oxide_thickness": {"mean": 0.075, "ci90": [0.0726, 0.0774], "mean_ratio": 1.25, "p_deviated": 1.0, "unit": "um"}, "body_dose": {"…": "…"}, "epi_doping": {"…": "…"}},
   "next_measurement": {"recommendation_code": "none_needed", "recommendation_label": "추가 측정 불필요 (이미 판정됨)"},
   "compensation": {"route": "tcad_verify", "high_confidence": false, "confidence_blockers": ["CHANGE_TOO_LARGE"],
                    "confidence": 0.948, "changes": {"body_dose": -0.09, "oxide_thickness": -0.15}, "factors": {"body_dose": 0.91, "oxide_thickness": 0.85},
                    "p_vth_in_spec_after": 1.0, "p_bv_in_spec": 1.0, "requires_human_approval": true},
   "fit": {"poor_fit": false}, "refine": {"requested": false, "performed": false}},
 "tcad_proposal": {"status": "proposed", "requires_human_approval": true, "high_confidence": false,
                   "candidates": [{"name": "보정 후 (사후 평균 상태)",
                                   "process_parameters": {"body_dose": 7.012e12, "epi_doping": 1.7e16, "oxide_thickness": 0.06375},
                                   "predicted_outputs": {"vth": 2.229, "gm": 4.456, "id_on": 5.15, "bv": 41.81}}]}}
```

### 응답을 읽는 법

| `compensation.route` | 의미 | `tcad_proposal` | Gateway의 동작 |
|---|---|---|---|
| `apply` | 임계값 5개를 모두 통과. TCAD를 건너뛰고 보정값 적용 후보 | null (보정값은 `compensation.target_process_parameters`) | 관리자 승인 후 보정 명령 (TCAD 요청 없음) |
| `tcad_verify` | 임계값을 하나라도 못 채움. TCAD 검증 필요 | 있음 | TCAD 워크스테이션에 검증 요청 → 결과 저장 → 관리자 승인 |
| `no_action` | 정상, 보정 불필요 | null | 결과만 저장 |
| `manual` | 학습하지 않은 유형(`POOR_FIT`), 사람이 판단 | null | 관리자 검토 대기 |

- `high_confidence`: 임계값 5개를 모두 통과했는가 (보정 후 규격 확률 ≥ 0.99, 원인 확률 ≥ 0.90, 보정량 ≤ ±15 %, 에피 이탈 확률 ≤ 0.05, 보정 후 변수 0.70~1.30, 임시 기준). `apply`는 이 값이 true일 때만 나온다. 못 채운 조건은 `confidence_blockers`에 나온다. `변환기.py`의 `SKIP_TCAD_WHEN_HIGH_CONFIDENCE`를 False로 하면 보정 후보가 전부 `tcad_verify`가 된다.
- `decided: false`면 원인이 확실하지 않다는 뜻이다. `next_measurement`가 "BV를 재라", "웨이퍼 수를 늘려라" 같은 권고(`measure_bv`, `more_wafers_2x`, `more_wafers_4x`)를 준다.
- 분류 코드 8개: `normal`, `dose`, `epi`, `oxide`, `dose+epi`, `dose+oxide`, `epi+oxide`, `dose+epi+oxide`.

## A-5. 시나리오 3: TCAD 검증 (Gateway ↔ TCAD 워크스테이션) — 초안

TCAD 쪽 HTTP 서비스는 아직 없고, 아래는 팀이 합의해야 할 **초안**이다. 입력은 `tcad_proposal.candidates[i]`, 결과는 현재 실행기(`대량실행.py`)가 내는 필드 기준이다.

요청:
```json
{"request_id": "tcad-001", "job_id": "job-2", "candidate_name": "보정 후 (사후 평균 상태)",
 "process_parameters": {"body_dose": 7.012e12, "epi_doping": 1.7e16, "oxide_thickness": 0.06375},
 "requested_outputs": ["vth", "gm", "id_on", "bv"]}
```
결과:
```json
{"request_id": "tcad-001", "status": "succeeded",
 "result_payload": {"vth": 2.31, "gm": 4.52, "id_on": 5.12, "bv": 41.1},
 "metadata": {"seconds_iv": 491, "seconds_bv": 1234, "attempts": 1}}
```
소요 시간은 샘플당 약 30분(IV 약 8분 + BV 약 20분). Gateway의 제한 시간은 90분 이상으로 잡는다. 결과 규격 판정(Vth 1.7~2.6 V, BV 40 V 이상)은 Gateway가 한다.

## A-6. 오류 코드

| 코드 | HTTP | 의미 |
|---|---|---|
| `INVALID_INPUT` | 400 | 필드 누락, 음수, 알 수 없는 필드, JSON 오류 |
| `UNSUPPORTED_CONTRACT_VERSION` | 400 | `model_contract_version`이 fab-ml-v1이 아님 |
| `UNSUPPORTED_TASK_TYPE` | 400/501 | 지원하지 않는 `task_type`, 또는 진단 기능이 꺼져 있음 |
| `OUT_OF_DOMAIN` | 200 | 학습 범위 밖 입력 (`status: failed`, 값 없음) |
| `MODEL_NOT_READY` | 501 | 진단 모델 로딩 실패 |
| `UNAUTHORIZED` | 401 | 토큰 불일치 |
| `INFERENCE_FAILED` | 500 | 예기치 못한 내부 오류 |

같은 `request_id`를 다시 보내면 계산하지 않고 이전 응답을 그대로 돌려준다 (Worker 재시도 대응). 시험할 때는 **요청마다 `request_id`를 바꿔야** 새로 계산된다.

# B. 테스트 과정

## B-1. 테스트 층

| 층 | 무엇을 확인 | 어디서 | 명령 |
|---|---|---|---|
| 1 | 서비스 코드와 계약 (52개 항목) | 개발 PC | `cd 통신 && python 시험.py` |
| 2 | Jetson 환경과 파일 | Jetson | `python3 check_env.py` |
| 3 | 모델 불러오기, 예측·진단 한 번씩 | Jetson | `python3 check_env.py --smoke` |
| 4 | Jetson에서 서비스 자체 시험 (52개) | Jetson | `cd 통신 && python3 시험.py` |
| 5 | 서버를 실제로 켜고 Worker 대역으로 호출 | Jetson | `python3 run_service.py` + `python3 worker_stub.py` |
| 6 | 속도·재현성 | Jetson | `최종ML/jetson_벤치.py`, `jetson_검증.py` |
| 7 | 실제 Worker 연동 | Worker/Gateway | Worker가 `/api/v1/predict`·`/api/v1/diagnose` 호출 |
| 8 | TCAD 검증 대조 | TCAD PC | 아래 B-3 |

**상태**: 1층(52개 항목)은 PC에서 통과했다. 2~5층은 이전 번들(39개 항목)에서 Jetson 통과를 확인했고, 재부팅 후 자동 시작과 새 번들(B안 정책 반영)의 요청 3종 응답도 팀원이 확인했다. 현재 52개 항목 전체를 Jetson에서 돌린 결과는 아직 받지 못했다. 7층(실제 Worker)과 8층의 자동화는 아직 하지 않았다.

## B-2. 합격 기준

| 확인 | 합격 |
|---|---|
| `check_env.py` | 모든 항목 통과, "서비스를 켤 수 있다" |
| `시험.py` | 마지막 줄 "전체 판정: 모두 통과" |
| `worker_stub.py` | "전체 판정: 모두 통과" |
| 기준값 예측 | vth 2.26 V, gm 4.60 µS/µm, id_on 5.21 µA/µm, bv 41.1 V |
| 영역 밖 입력 | HTTP 200, `OUT_OF_DOMAIN` |
| 진단 소요 시간 | 수 초 (Jetson에서 약 3~4초, 이 PC 약 2.7초). Worker 제한 시간은 60초 이상 |
| 같은 `request_id` 재요청 | 이전 응답과 동일 |

## B-3. TCAD 대조 테스트 (모델 예측이 TCAD와 맞는지)

모델이 내놓은 후보를 TCAD로 직접 계산해서 `predicted_outputs`와 비교하는 시험이다.

1. 진단 응답의 `tcad_proposal.candidates[i].process_parameters`를 가져온다.
2. TCAD PC에서 그 공정값으로 deck를 돌린다 (현재는 `대량작업2/샘플링계획`의 계획표 형식으로 한 줄 만들고 `대량실행.py run`).
3. 결과의 Vth, gm, Id, BV를 `predicted_outputs`와 비교한다.
4. 판정: Vth 오차가 약 25 mV 이내, gm과 Id 오차가 약 2.5 % 이내, BV 오차가 약 0.15 V 이내이면 서로게이트의 예측이 맞는 것이다 (모델 목표 기준).
5. TCAD 결과가 규격 안(Vth 1.7~2.6 V, BV 40 V 이상)이면 보정이 성공한 것이다.

기준값 근처 작은 이탈 샘플 36개를 TCAD로 돌려서 `high_confidence`의 오판율을 재는 평가가 진행 중이다 (`진단에이전트/소이탈평가.py`).

## B-4. 테스트 명령 모음 (Jetson, 서비스가 켜진 상태)

`/opt/fabrx` 또는 `/home/jetson/project/surrogate_ml/fabrx`에서 (C-1 참고). 요청 파일을 먼저 만든다.

```bash
cat > /tmp/predict.json <<'EOF'
{"schema_version":1,"task_type":"surrogate","request_id":"t-001","job_id":"job-1","run_id":"run-1","attempt":1,"model_contract_version":"fab-ml-v1","surrogate_mode":"prod","input_payload":{"process_parameters":{"body_dose":7.7e12,"epi_doping":1.7e16,"oxide_thickness":0.06},"requested_outputs":["vth","gm","id_on","bv"]}}
EOF
cat > /tmp/diagnose.json <<'EOF'
{"schema_version":1,"task_type":"diagnosis","request_id":"d-001","job_id":"job-2","run_id":"run-1","attempt":1,"model_contract_version":"fab-ml-v1","surrogate_mode":"prod","input_payload":{"measurements":{"vth":2.874,"gm":3.767,"id_on":3.468,"bv":44.186},"n_wafers":25,"refine":false}}
EOF
```
```bash
curl -s http://127.0.0.1:8300/health/ready
curl -s -X POST http://127.0.0.1:8300/api/v1/predict -H "Content-Type: application/json" --data @/tmp/predict.json
curl -s -X POST http://127.0.0.1:8300/api/v1/diagnose -H "Content-Type: application/json" --data @/tmp/diagnose.json
```
결과를 보기 좋게: `... | python3 -m json.tool`. 토큰을 쓰는 경우 `-H "X-Fab-Token: 영문토큰"`을 추가한다. 같은 `request_id`로 다시 보내면 캐시된 응답이 오니, 새로 계산하려면 `t-002`처럼 바꾼다.

영역 밖 시험:
```bash
sed 's/"t-001"/"t-oob"/; s/7.7e12/3.2e13/; s/1.7e16/1.0e16/; s/0.06}/0.05}/' /tmp/predict.json | curl -s -X POST http://127.0.0.1:8300/api/v1/predict -H "Content-Type: application/json" --data @- | python3 -m json.tool | head -12
```
`error_code`가 `OUT_OF_DOMAIN`이면 정상이다.

# C. Jetson 서버 운영

## C-1. 위치와 구성

| 항목 | 위치·이름 |
|---|---|
| 설치 폴더 | `/home/jetson/project/surrogate_ml/fabrx` (팀원 보고 기준. `ls`로 확인할 것. 처음 문서의 `/opt/fabrx`일 수도 있다) |
| 진입점 | `python3 run_service.py` |
| systemd 서비스 | `fabrx-model.service` (부팅 시 자동 시작 **[확인됨]**, 재부팅 시험 완료) |
| 서비스 정의 파일 | `/etc/systemd/system/fabrx-model.service` |
| 토큰 설정 | `/etc/fabrx/service.env` (`FAB_SERVICE_TOKEN=영문토큰`, 없으면 토큰 없이 동작) |
| 로그 | `/var/log/fabrx/model-service.log`, `journalctl -u fabrx-model` |
| 접속 주소 | `127.0.0.1:8300` (Jetson 안에서만. 외부 접속 불가) |
| 백업 | 재배포 때 만든 `fabrx_bak_<날짜>` 폴더 (롤백용) |

## C-2. 서버를 끄고 켜기 (systemd) **[표준 명령]**

```bash
sudo systemctl status fabrx-model        # 상태 (active (running) 이면 정상)
sudo systemctl stop fabrx-model          # 끄기
sudo systemctl start fabrx-model         # 켜기
sudo systemctl restart fabrx-model       # 다시 켜기
sudo systemctl is-enabled fabrx-model    # enabled 이면 부팅 때 자동 시작
sudo systemctl enable fabrx-model        # 자동 시작 켜기
sudo systemctl disable fabrx-model       # 자동 시작 끄기
```
`systemctl is-active fabrx-model`은 `active`가 나와야 한다.

**켠 직후 바로 `ready`가 되지 않는다.** 서비스는 시작할 때 모델을 불러오고 진단용 후보 격자를 한 번 계산해서 수 초가 걸린다. 아래처럼 `ready`가 될 때까지 기다린다.

```bash
until curl -s http://127.0.0.1:8300/health/ready | grep -q '"status": "ready"'; do sleep 2; done; echo ready
```

## C-3. 껐다 켠 뒤 확인 순서 (복사해서 위에서부터 실행)

```bash
sudo systemctl is-active fabrx-model                      # 1. active
ss -ltnp | grep 8300                                      # 2. 127.0.0.1:8300 에서 LISTEN
curl -s http://127.0.0.1:8300/health                      # 3. status ok, contract fab-ml-v1
curl -s http://127.0.0.1:8300/health/ready                # 4. status ready, surrogate_ready/diagnosis_ready true
curl -s -X POST http://127.0.0.1:8300/api/v1/predict -H "Content-Type: application/json" --data @/tmp/predict.json     # 5. 기준값 예측
curl -s -X POST http://127.0.0.1:8300/api/v1/diagnose -H "Content-Type: application/json" --data @/tmp/diagnose.json   # 6. 진단
cd /home/jetson/project/surrogate_ml/fabrx && python3 worker_stub.py                                                    # 7. 모두 통과
tail -n 30 /var/log/fabrx/model-service.log                                                                              # 8. 오류 로그 없음
```
(요청 파일 `/tmp/*.json`은 B-4에서 만든다. 재부팅하면 `/tmp`가 비워질 수 있으니 다시 만든다.)

기대값:
- 3번: `"status": "ok"`, `"contract": "fab-ml-v1"`, `"spec": {…, "status": "datasheet_AOI4184"}`
- 4번: `"status": "ready"`, `loaded_models`에 모델 2개, `model_load_duration_ms`
- 5번: `"vth": 2.26…`, `"bv": 41.1…`, `"status": "succeeded"`
- 6번: `"top_category": "oxide"`, `"route": "tcad_verify"`, `tcad_proposal` 있음

## C-4. 재부팅했을 때 확인 **[확인됨: 재부팅 시험 완료]**

```bash
sudo reboot
# 다시 접속한 뒤
sudo systemctl is-active fabrx-model        # active 이면 자동 시작 성공
until curl -s http://127.0.0.1:8300/health/ready | grep -q ready; do sleep 2; done; echo ready
```
Jetson 부팅 직후에는 네트워크와 디스크가 준비되는 시간이 있어서 `ready`까지 수십 초가 걸릴 수 있다.

## C-5. 서비스 없이 직접 켜서 보기 (디버깅)

systemd가 포트를 쓰고 있으면 직접 켤 수 없으니 먼저 멈춘다.

```bash
sudo systemctl stop fabrx-model
cd /home/jetson/project/surrogate_ml/fabrx
export LANG=C.UTF-8 LC_ALL=C.UTF-8
python3 run_service.py                      # 화면에 로그가 나온다. 끝내려면 Ctrl+C
python3 run_service.py --token 영문토큰      # 토큰을 쓸 때
python3 run_service.py --no-agent           # 진단 없이 서로게이트만
```
끝나면 `sudo systemctl start fabrx-model`로 서비스를 다시 켠다. 다른 터미널에서 C-3의 확인 명령을 실행한다.

## C-6. 문제 해결

| 증상 | 확인·조치 |
|---|---|
| `active`가 아님 | `sudo journalctl -u fabrx-model -n 50 --no-pager`로 원인 확인 |
| 포트 8300 사용 중 (직접 켰을 때) | `ss -ltnp \| grep 8300`으로 확인. systemd가 쓰고 있으면 `sudo systemctl stop fabrx-model` |
| `curl`이 연결 거부 | 서비스가 아직 로딩 중이거나 꺼져 있음. 10~20초 후 재시도, `systemctl status` 확인 |
| 401 `UNAUTHORIZED` | `/etc/fabrx/service.env`에 토큰이 있음. 요청에 `X-Fab-Token` 헤더 추가 |
| `OUT_OF_DOMAIN` | 단위(도즈 cm⁻², 에피 cm⁻³, 산화막 µm)와 값이 기준값(7.7e12, 1.7e16, 0.06) ±30 % 근처인지 |
| 같은 응답만 온다 | `request_id`를 바꾸지 않아 캐시된 응답이다. `request_id`를 바꾼다 |
| 한글 파일명 오류 (`ModuleNotFoundError`) | `export LANG=C.UTF-8 LC_ALL=C.UTF-8` 후 다시 실행 |
| 진단이 느림 | 사후분포가 좁은 경우 길어진다 (수 초~십수 초). Worker 제한 시간 60초 이상 |
| 고정밀 모드(`refine: true`)가 안 됨 | 정상. Jetson에 `tabpfn`이 없어 기본 모드로 대체되고, 응답의 `refine.performed`가 false와 사유로 표시된다 |

## C-7. 새 버전 배포와 롤백 **[팀원이 수행한 절차]**

PC에서 번들을 만든다 (`통신/번들만들기.py`, 결과 `Jetson배포/fabrx_jetson.tar.gz`).

```bash
scp fabrx_jetson.tar.gz <사용자>@<Jetson 주소>:~/
ssh <사용자>@<Jetson 주소>
sudo systemctl stop fabrx-model
mv /home/jetson/project/surrogate_ml/fabrx /home/jetson/project/surrogate_ml/fabrx_bak_$(date +%Y%m%d_%H%M%S)    # 백업
tar xzf ~/fabrx_jetson.tar.gz -C /home/jetson/project/surrogate_ml
cd /home/jetson/project/surrogate_ml/fabrx && export LANG=C.UTF-8 LC_ALL=C.UTF-8 && python3 check_env.py        # 점검
sudo systemctl start fabrx-model
```
이후 C-3의 확인 순서를 실행한다.

롤백: 서비스를 멈추고 새 폴더를 치운 뒤 `fabrx_bak_…`를 `fabrx`로 되돌리고 서비스를 시작한다. 폴더 위치가 바뀌면 systemd 정의 파일의 경로도 달라지므로, 위치를 옮겼다면 `sudo ./install_service.sh install`을 다시 실행한다 (실행 전에 직접 켠 서비스는 끈다).

## C-8. 기록해 둘 것 (문제가 생겼을 때 팀에 전달)
- `sudo systemctl status fabrx-model` 출력과 `journalctl -u fabrx-model -n 50` 출력
- `/var/log/fabrx/model-service.log` 마지막 50줄
- `curl http://127.0.0.1:8300/health/ready` 응답
- 문제가 된 요청 JSON과 응답 JSON
- `python3 check_env.py` 출력
- 마지막으로 배포한 번들의 `manifest.json` 날짜 (또는 `fabrx_bak_…` 백업 폴더 이름)
