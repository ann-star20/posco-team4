## 팀 소개

안녕하십니까, 저희 팀을 먼저 소개하겠습니다. 저희는 세 명이 파트를 나눠 FabRx를 만들었습니다.

- **AOI·인프라·통신 파트** — 황은정: AOI 외관검사 비전 모델, Camera/AOI WebSocket, Event Gateway, ROS 2 통신, DB 스키마 설계를 맡았습니다.
- **Unity·대시보드 파트** — 호예찬(팀장): Unity 가상 팹 에셋 제작, 가상 공장 시뮬레이터, AOI/ML 검사 요청, 결과 대시보드를 맡았습니다.
- **모델링·TCAD 검증 파트** — 차주현: MOSFET EDA, 서로게이트·진단 에이전트 모델링, TCAD 검증 서버를 맡았습니다.

## Chapter 1. 프로젝트 배경

### 1-1. 당면 과제

반도체 공정에는 세 가지 구조적인 문제가 있습니다.

**첫째, 연쇄 오차입니다.** 초미세화와 3차원 구조로 공정이 복잡하게 연결되면서, 앞선 공정의 미세한 변화가 후속 공정 결과에 그대로 영향을 줍니다. 포토, 식각, 박막 증착, 이온주입처럼 수많은 공정이 순차적으로 이어지기 때문에, 한 공정의 오차가 뒤 공정으로 누적됩니다.

**둘째, 실험 비용입니다.** 지금까지는 숙련된 엔지니어의 경험과 실제 웨이퍼를 이용한 반복 실험에 의존해 최적 조건을 찾아왔습니다. 그런데 소자가 미세해질수록 이 실험에 드는 시간과 웨이퍼 비용이 계속 늘어나고 있습니다.

**셋째, 닫힌 데이터입니다.** 공정 데이터는 기업의 핵심 기술정보라, 대규모 생산시설과 데이터를 가진 대기업이 아니면 중소기업·대학·연구기관은 공정 최적화 기술을 자체적으로 확보하기가 어렵습니다.

### 1-2. 자율팹이란?

이 문제들에 대한 업계의 답이 **자율팹**입니다. 공정 데이터를 연결해, 지금까지 사람이 해오던 "이상 대응"의 판단을 AI가 돕는 팹입니다. 흐름은 이렇습니다 — 공정 예측(가상 환경에서 결과를 사전 시험) → 이상 감지(측정값 변화를 즉시 포착) → 원인 진단(원인 후보를 확률로 추정) → 보정안 제시(조정안 제안과 사전 검증) → 엔지니어 승인(최종 판단은 사람이) → 기존 시스템 연동(승인 후 레시피에 적용), 이렇게 여섯 단계로 이어집니다.

이 중에서 저희 프로젝트가 다루는 범위는 **원인 진단과 보정안 제시, 그리고 엔지니어 승인**까지입니다. 공정 예측과 이상 감지, 기존 시스템 연동은 범위 밖입니다. 이 부분은 뒤에서 더 구체적으로 짚어드리겠습니다.

### 1-3. 업계 동향

실제로 국내 대기업들도 이 방향으로 움직이고 있습니다. SK하이닉스는 2030년 자율형 팹 구축을 목표로, 판단을 맡는 오퍼레이션 AI, 실행을 맡는 피지컬 AI, 가상 검증을 맡는 디지털 트윈을 세 축으로 추진 중이며, 오퍼레이션 AI로 설비 유지보수·결함 분석 처리 시간을 50% 이상 줄였다고 밝혔습니다. 삼성전자도 2030년까지 생산 공장을 AI 자율 공장으로 전환하는 것을 추진하며, 평택 1공장을 디지털 트윈으로 구현해 생산 흐름을 사전 검증하고 이상징후가 생기면 로봇을 투입해 대응하는 방식을 GTC 2026에서 제시했습니다.

즉 "양산 중 이상에 AI로 대응한다"는 방향 자체는 이미 업계가 가고 있는 길입니다. 저희 프로젝트는 그 흐름 안에서, 중소 규모에서도 검증해볼 수 있는 작은 단위의 시도라고 보시면 됩니다.

## Chapter 2. 프로젝트 개요

### 2-1. 프로젝트 방향성

업계 사례를 조금 더 구체적으로 보면, 공공·민간이 함께 만든 **알스피어(Alsphere)** 같은 사례가 있습니다. 알스피어는 알세미·나노종합기술원·KISTI가 공동 개발한 반도체 공정 AI 플랫폼으로, 가상 환경에서 공정 조건의 결과를 먼저 예측해 실험을 줄이는 데 초점이 맞춰져 있습니다. 실제 나노팹 데이터로 포토·식각·박막·이온주입 4대 공정의 AI 모델을 만들었고, 실험 결과와 비교한 평균 예측 정확도가 91.7%라고 발표했습니다.

저희가 본 지점은 이것입니다. 알스피어나 SK하이닉스의 오퍼레이션 AI, 삼성의 이상징후 대응 사례처럼, "공정 조건을 넣으면 결과가 어떻게 나올지" 예측하거나 "이상이 생기면 대응"하는 것은 이미 업계가 다루고 있는 문제입니다. 그런데 **양산 중 이상이 났을 때, 이미 정해 둔 조건이 정확히 어디서 얼마나 틀어졌는지를 거꾸로 찾아내는 것**은 방향이 반대인, 또 다른 문제입니다. 측정값에서 원인이 되는 공정 노브를 확률로 추정하고, 확신이 없으면 "구분 불가"라고 솔직하게 답하고, 도즈·산화막 같은 조정안을 제시하고, 기준에 미달하면 TCAD 재검증까지 요청하는 일입니다.

저희는 이 부분을 실제 팹 데이터 없이, **TCAD 합성 데이터로 먼저 검증**하는 방식으로 접근했습니다.

### 2-2. FabRx

그 결과물이 **FabRx**입니다. 서로게이트가 공정 조건에서 전기 특성을 예측하고, 진단 에이전트가 측정값에서 원인을 확률로 추정하고, 보정안과 TCAD 재검증을 거쳐, 최종적으로 엔지니어가 승인하는 흐름입니다. 한 줄로 요약하면 — **알스피어가 공정 조건의 결과를 예측한다면, FabRx는 결과에서 원인을 거꾸로 추정합니다.**

실제 팹 데이터를 얻기 전에, TCAD 합성 데이터로 학습한 서로게이트와 진단 에이전트만으로도 양산 중 이상의 원인을 확률로 좁히고 보정안을 제시할 수 있는지, 시뮬레이션으로 먼저 확인하는 것이 이 프로젝트의 핵심입니다. 그리고 운영 라인에 조금 더 가까운 환경을 만들기 위해, 완제품 MOSFET의 외관검사(AOI)와 3D 가상 팹 모니터링도 함께 구성했습니다.

### 2-3. Alsphere vs FabRx

두 프로젝트를 나란히 놓고 비교하면, 저희의 차별점과 한계가 함께 분명해집니다.

| 구분 | Alsphere | FabRx |
| --- | --- | --- |
| 대상 | 공정 개발 — "어떤 조건으로 만들 것인가" | 양산 중 이상 — "어디가 틀어졌는가" |
| 방향 | 조건 → 결과 예측 (정방향), 실험 감축 | 결과 → 원인 추정 (역방향) + 보정안 제시 |
| 데이터 | 물리 시뮬레이션 + 실제 팹 데이터 | TCAD 합성 데이터, 실제 데이터 없이 시작 |
| 검증 | 4대 공정 평균 예측 정확도 91.7% (실증 완료) | 합성 데이터 교차검증, 실데이터는 다음 단계 |

이 비교에서 솔직하게 인정해야 할 부분이 있습니다. 알스피어는 실제 나노팹 데이터로 4대 공정에 대해 실증까지 마친 플랫폼이고, FabRx는 아직 TCAD 합성 데이터로 시뮬레이션 검증을 마친 단계입니다. 규모나 성숙도에서 같은 선상에 놓고 비교할 수 있는 상대는 아닙니다.

그럼에도 저희가 의미 있다고 생각하는 지점은 **다루는 문제 자체가 다르다**는 것입니다. 알스피어가 공정 개발 단계에서 "조건을 넣으면 결과가 어떻게 나올까"를 예측하는 정방향 문제를 푼다면, FabRx는 양산 단계에서 "결과가 이상한데 원인이 뭘까"를 되짚는 역방향 문제를 풉니다. 이 역방향 문제는 데이터를 구하기도, 검증하기도 더 어렵기 때문에 저희는 실제 팹 데이터 없이도 시작할 수 있는 방법 — TCAD로 합성 데이터를 직접 만들고, 그 위에서 모델이 통하는지를 먼저 확인하는 방법을 택했습니다. 다음 장에서 그 구체적인 구조를 설명드리겠습니다.

## Chapter 2-4. 프로젝트 개요 — FabRx 프로젝트 동작

안녕하십니까, 지금부터 저희가 구축한 FabRx 가상 공정 시스템을 소개하겠습니다.

저희 시스템은 세 단계로 동작합니다. **예측(Predict) → 진단(Diagnose) → 판단(Decide)** 입니다.

먼저 **예측** 단계입니다. 공정 노브 3개 — 바디 도즈, 에피 도핑, 산화막 두께 — 를 입력하면, 서로게이트 ML 모델이 즉시 Vth, gm, Id, BV를 계산해 돌려줍니다. 여기서 중요한 점은, 이 모델이 학습한 범위 밖의 입력이 들어오면 억지로 값을 내지 않고 "모른다"고 답한다는 것입니다. 잘못된 확신을 주지 않도록 설계했습니다.

다음은 **진단** 단계입니다. 예측 결과가 불량으로 판정되면, 진단 에이전트가 어떤 공정 변수가 문제인지 노브별로 확률을 추정하고 보정안을 제시합니다. 이때도 확신도가 70% 미만이면 "구분 불가"로 솔직하게 답합니다.

마지막은 **판단** 단계입니다. 진단 에이전트가 낸 보정안을 5개의 임계값 조건으로 검사합니다. 모두 통과하면 TCAD 정밀 검증을 생략할 수 있는 후보로 분류하고, 하나라도 미달이면 실제 TCAD 재검증을 요청합니다. 그리고 최종적으로 공정에 적용할지는 반드시 엔지니어가 승인합니다. AI가 모든 걸 자동으로 결정하지 않고, 사람이 마지막 의사결정을 하는 구조입니다.

## Chapter 3. 기술 아키텍처

### 3-1. 모델 사용 배경

#### (1) 왜 서로게이트가 필요한가 — TCAD 대신 빠른 모델이 필요한 이유

진단 에이전트가 하는 일은 "측정값(Vth, gm, Id, BV)이 들어오면, 어떤 공정 조건이었어야 이 값이 나왔을지를 후보 조건마다 계산해보는 것"입니다. 그런데 이걸 TCAD로 직접 하면 현실적으로 불가능합니다.

TCAD 한 점을 계산하려면, 먼저 공정 시뮬레이션으로 소자 구조를 만들고 그 구조로 소자 시뮬레이션을 돌려 전기 특성을 계산합니다. 전류 곡선만 구하는 데 5~8분, 항복전압(BV)까지 포함하면 16~21분이 걸려서 합쳐 **20~30분**이 걸립니다. 정확하지만, 한 조건씩 밖에 계산할 수 없습니다.

반면 서로게이트는 TCAD 결과로 미리 학습해 둔 빠른 대역 모델이라, 공정 노브 3개를 넣으면 전기 특성 4개와 불확실도를 **0.4ms**, Jetson 실제 환경에서도 1점당 약 0.9ms 만에 계산합니다.

이 차이가 왜 중요하냐면, 진단은 한 번 돌릴 때 원인 확률과 보정안을 내기 위해 후보 조건을 **수만 번** 계산해야 하기 때문입니다. 예를 들어 후보 1만 개를 TCAD로 직접 평가한다고 하면 약 **170일**이 걸리지만, 같은 작업을 서로게이트로 하면 약 **4초**면 끝납니다. TCAD의 정확도는 그대로 활용하면서 속도만 바꿔치기한 셈인데, 이게 가능한 이유는 서로게이트가 TCAD를 대체하는 게 아니라 **TCAD 결과를 학습해서 흉내 내는 모델**이기 때문입니다. 즉 진단 에이전트가 현실적인 시간 안에 수만 개 후보를 평가할 수 있으려면, 서로게이트처럼 TCAD 급 정확도를 밀리초 단위로 내는 모델이 반드시 있어야 합니다.

#### (2) 서로게이트의 입력과 출력

이렇게 만든 모델이 **서로게이트(Surrogate) 모델**이고, 구조는 2단 가우시안 프로세스(**2단 GP**)입니다.

- **입력**: 노브 3개 — 바디 도즈 / 에피 도핑 / 산화막 두께
- **출력**: 4개 + 불확실도(σ) — Vth · gm / Id(4V) · BV / + 불확실도

그리고 중요한 동작 원칙이 하나 더 있습니다. **학습 영역 밖이면 값을 내지 않고 거절합니다.** 노브 값이 학습 때 본 범위를 벗어나면 억지로 숫자를 내는 대신 "모른다"고 답하도록 만들었습니다. 목표는 "빠르고, 정확하고, 모를 때는 모른다고 말하는 모델"입니다.

이 모델이 왜 2단 GP로 결정됐는지는 다음 절에서 대상 소자, 데이터 생성, 모델 선정 근거를 순서대로 자세히 설명드리겠습니다.

### 3-1-1. 대상 소자와 TCAD 구조

서로게이트가 다루는 대상 소자는 **AOI4184, 40V급 N채널 트렌치 MOSFET**입니다. 벅컨버터 안에 들어가는 소자로, 데이터시트 기준 VDS 40V, ID 50A, RDS(on) 8mΩ 미만(VGS 10V 조건)입니다. 저희가 실제로 규격 판정에 쓰는 값은 Vth 1.7~2.6V, BV 40V 이상 두 가지이고, gm과 Id는 합격/불합격 기준이 없는 대신 "원인이 어디 있는지"를 가려내는 진단용 지표로 씁니다.

이 소자를 TCAD(Silvaco Athena/Atlas)로 재현할 때 구조 설계에서 고비가 하나 있었습니다. 트렌치 MOSFET 반 셀 구조에서 노브 3개 — 폴리 게이트 쪽의 바디 도즈, 실리콘 쪽의 에피 도핑, 게이트 산화막의 두께 — 를 배치하는데, 실제 공정 순서(도핑 전에 마스크를 먼저 씌우는 순서)를 그대로 따르면 TCAD 상에서 게이트 쪽으로 도핑이 새어 들어가는 문제가 있었습니다. 이를 해결하기 위해 ①도핑을 먼저 하고 ②트렌치를 식각한 뒤 ③산화막·폴리를 올리는 순서로 바꿨습니다. 트렌치를 식각하는 과정 자체가 마스크 역할을 하기 때문에, 가릴 대상이 없어져 도핑이 새지 않는 구조입니다. 실제 팹의 공정 순서는 아니지만, TCAD에서는 "중간 과정이 달라도 최종 구조만 같으면 된다"는 방법론이 통용되기 때문에 채택한 방식입니다.

### 3-1-1-1. MOSFET 구조도로 보는 노브 3개의 위치

지금 화면에 보이는 것이 방금 말씀드린 트렌치 MOSFET 반 셀의 실제 단면 구조도입니다. 세 가지 색으로 영역을 구분했습니다. **노란색이 폴리 게이트, 파란색이 게이트 산화막, 주황색이 실리콘(바디·에피 영역)**입니다.

이 구조도 위에 공정 노브 3개가 각각 어디에 대응하는지 짚어보면 이렇습니다.

- **산화막 두께**: 파란색으로 표시된 게이트 산화막의 두께입니다. 기준값은 **0.06µm**로, 이 값이 Vth와 gm·Id를 가장 크게 움직이는 변수라고 앞서 EDA에서 말씀드린 바로 그 노브입니다.
- **바디 도즈**: 주황색 실리콘 영역 중 폴리 게이트와 맞닿은 바디(body) 쪽에 주입하는 붕소 임플란트 도즈입니다. 기준값은 **7.7e12 /cm²**입니다.
- **에피 도핑**: 주황색 실리콘 영역의 아래쪽, 에피택셜층 전체의 인(phosphorus) 농도입니다. 기준값은 **1.7e16 /cm³**이고, 이 농도가 항복전압(BV)을 거의 단독으로 결정한다는 것도 앞서 EDA에서 확인한 내용입니다.

즉 이 구조도 한 장이 "노브 3개가 물리적으로 어디에 있고, 왜 서로 다른 출력에 영향을 주는지"를 한눈에 보여줍니다. 바로 다음에 설명드릴 학습 데이터는, 이 세 노브의 값을 기준값 대비 비율로 바꿔가며 TCAD로 반복 계산해서 만든 것입니다.

### 3-1-2. 학습 데이터 생성과 EDA

**먼저 전체 규모입니다.** TCAD로 바디 도즈·에피 도핑·산화막 두께를 바꿔가며 총 **188개** 샘플을 계산했습니다. 기준값 주변 ±30% 범위에서 모두 고르게 뽑은 "코어" 샘플 **96행**, 한 노브만 ±30% 바깥으로 보내 학습 범위를 바깥쪽으로 넓힌 "확장" 샘플 **50행**, 노브 하나만 ±10~70%까지 더 넓게 바꿔 범위 밖 예측을 시험하기 위한 "단일 노브" 샘플 **42행**으로 구성됩니다. 이 중 학습 영역을 완전히 벗어난 3행을 제외한 **185행**을 실제 학습에 사용했고, BV(항복전압)는 계산 비용이 커서(샘플당 16~21분) 전체가 아니라 **88행**에만 계산했습니다.

데이터를 만든 뒤 바로 모델링에 들어가지 않고, 노브 하나씩 따로 본 데이터와 세 노브를 한꺼번에 섞은 데이터를 각각 들여다봤습니다.

**단일 노브 데이터 — "곡선은 매끄럽지만 휘어 있다."** 노브 하나만 바꿔가며 그린 Vth·BV 곡선을 보면 두 가지가 뚜렷합니다. 첫째, 점과 점 사이가 꺾임 없이 부드럽게 이어져서 적은 점만으로도 그 사이를 메울 수 있다는 것이고, 둘째, 그 곡선이 **직선이 아니라는** 것입니다. 실제로 직선으로 이어서 맞추면 Vth 오차가 목표 성능의 **2배**까지 벌어집니다. TCAD 한 번 계산에 20~30분이 걸려서 점 자체는 143개(BV는 64개)로 많지 않습니다. 그래서 "적은 점 사이를 매끄러운 곡선으로 채우면서, 그 사이를 얼마나 확신할 수 있는지도 같이 알려주는 모델"이 필요하다는 결론을 내렸고, 이것이 GP를 고른 첫 번째 근거입니다.

**대량 실행 데이터 — "Id는 Vth를 따라가지만, 완전히 같지는 않다."** Vth와 Id(4V)를 같은 전류 곡선에서 함께 뽑아보면, Vth가 오를수록 Id가 떨어지는 관계가 순위 상관 **−0.93**으로 매우 강하게 나타납니다. 하지만 완전히 한 몸은 아닙니다. 예를 들어 Vth가 똑같이 2.0V인 샘플들 사이에서도 Id는 3.9~6.7µA/µm로 갈립니다. 즉 "Id는 대부분 Vth로 설명되지만, 나머지는 산화막 등 다른 공정 노브가 추가로 정한다"는 뜻입니다. 그래서 Id를 처음부터 노브만으로 따로 맞히는 대신, **Vth를 먼저 예측하고 그 예측값을 노브와 함께 다시 넣어 Id를 예측하는 2단 GP 구조**를 만들었습니다. 이 구조가 Id를 처음부터 독립적으로 맞히는 것보다 더 정확했습니다.

**BV 데이터 — "BV는 에피 하나가 정한다."** BV와 세 노브 사이의 순위 상관을 보면 에피 도핑이 **−0.93**으로 압도적이고, 나머지 두 노브인 바디 도즈(0.01)와 산화막(0.33)은 BV에 거의 영향이 없습니다. Vth·gm·Id를 정하는 노브(주로 산화막·바디 도즈)와 BV를 정하는 노브(에피 도핑)가 서로 다르다는 뜻입니다. 그래서 BV가 있는 점만으로 따로 학습하는 **BV 전용 GP**를 별도로 만들어, Vth·gm·Id 모델과 서로 간섭하지 않도록 했습니다.

**잡음 대비 민감도 분석 — "작은 변화는 측정 잡음에 묻힌다."** 노브를 1%만 바꿨을 때 나오는 신호를 가정한 측정 잡음과 비교해보면, 가장 큰 신호(에피 도핑이 BV에 주는 영향)도 0.78로 잡음보다 작습니다. 즉 공정이 1% 정도 틀어져도 측정을 한 번만 해서는 잡음에 묻혀 보이지 않을 수 있다는 뜻입니다. 게다가 바디 도즈와 산화막은 Vth를 같은 방향으로 움직여서 측정값만으로는 어느 쪽이 원인인지 헷갈립니다. 그래서 예측값과 함께 "이 예측을 얼마나 확신하는지"도 같이 내고, 확신이 낮으면 TCAD로 다시 확인하도록 설계했습니다. 이것이 서로게이트가 불확실도(σ)를 반드시 함께 출력해야 하는 이유입니다.

이 네 가지 분석을 종합하면 다음과 같은 요구 조건으로 정리됩니다.

| EDA에서 발견한 것 | 모델에 주는 요구 조건 |
| --- | --- |
| 점이 적고, 곡선은 매끄럽지만 직선은 아니다 | 소량 데이터에 강하고 비선형을 학습하는 GP 계열이 유리 |
| Vth와 Id가 강하게 묶여 있다 (순위 상관 −0.93, 다만 완전히 같지는 않다) | Id는 Vth 예측값을 받는 2단 구조로 |
| BV는 에피 도핑이 거의 혼자 결정한다 (다른 노브는 0.01, 0.33) | BV는 Vth·gm·Id와 섞지 않는 별도 모델로 |
| 노브 1% 변화의 신호가 측정 잡음보다 작다, 도즈·산화막은 서로 헷갈린다 | 예측과 함께 믿을 만한 불확실도(σ)를 내야 한다 |

이 네 가지 요구 조건을 모두 만족하는 후보로 **GP(가우시안 프로세스) 계열**을 중심에 두고, 그래도 GP가 정말 최선인지 확인하기 위해 총 16종의 후보를 구성했습니다. 구성 비율은 GP 계열이 가장 많은 **7종**(입력 변환·2단 구조·잡음항 등을 바꾼 변형), 최신 사전학습 표 데이터 모델(TabPFN) 계열 **4종**, 신경망 계열 **2종**(MLP 앙상블, NVIDIA PhysicsNeMo), GP와 TabPFN을 섞은 하이브리드 **2종**, 트리 부스팅(LightGBM) **1종**입니다.

### 3-1-3. 후보 16종 비교와 공정한 시험

이 16종을 **같은 데이터, 같은 분할**로 여섯 가지 시험에 똑같이 통과시켰습니다. 요구 성능은 가정한 측정 잡음의 절반으로 잡았습니다(Vth 25mV, gm·Id 2.5%, BV 0.15V).

| 시험 | 보는 것 |
| --- | --- |
| ① 교차검증 | 학습 영역 안에서의 정확도 |
| ② 단일 노브 외삽 | 영역 밖으로 번질 때 얼마나 틀리는가 |
| ③ 방향별 외삽 | 한 번도 본 적 없는 방향에서의 정확도 |
| ④ 사후 검증 | 나중에 계산한 새 배치로 보는 진짜 시험 |
| ⑤ 잡음 학습 | 측정 잡음이 낀 데이터에서도 안정적인가 |
| ⑥ 불확실도 신뢰성 | 모델이 말하는 σ(불확실도)를 믿을 수 있는가 |

**결과는 뚜렷했습니다.** 교차검증에서 GP를 포함하지 않은 계열은 모두 Id(4V)에서 요구 성능을 넘겼습니다. 단일 노브를 영역 밖으로 보내는 외삽 시험에서는 2단 GP의 Vth 오차가 26.5mV인 반면, LightGBM은 490mV로 사실상 외삽이 불가능했습니다. 불확실도 신뢰성에서는 신경망 계열이 ±2σ 포함률 15~76%로 심하게 과신했고(이상적으로는 95%), 딥 GP는 반대로 99~100%로 지나치게 겁이 많았으며, TabPFN과 보정된 GP만 94~98%로 "말한 만큼 맞는" 정직한 모델이었습니다. 과적합 분석에서는 GP가 학습 오차는 거의 0이면서도 검증 오차는 16종 중 가장 낮은 "정상적인 보간"을 보였고, 신경망·트리 계열은 검증 오차가 학습 오차의 8~34배까지 벌어지는 뚜렷한 과적합을, 딥 GP와 TabPFN은 반대로 학습 점조차 잘 맞히지 못하는 과소적합을 보였습니다.

### 3-1-4. 최종 선정: 두 가지 모드

이 종합 비교 결과로 **2단 구조를 가진 GP**를 기본 모델로 선정했습니다. 다만 용도에 따라 두 가지 모드로 나눠 씁니다. 진단 에이전트가 후보 공정 조건 수만 개를 빠르게 훑어야 할 때는 **빠른 기본 모드**(2단 GP)를 쓰고, 그중 유력한 후보 하나를 마지막으로 다시 확인할 때는 GP와 TabPFN을 가중 평균한 **고정밀 모드**를 씁니다. 정확도와 속도를 동시에 만족시키기 위한 2단 구성입니다.

최종 교차검증 성능은 Vth 2.19mV(요구 25mV, 통과), gm 0.56%(요구 2.5%, 통과), Id(4V) 1.02%(요구 2.5%, 통과), BV 0.156V(요구 0.15V, 근소 미달)입니다. Vth·gm·Id 세 출력은 모델 오차가 가정 측정 잡음의 4~20% 수준밖에 되지 않을 만큼 여유 있게 통과했습니다.

### 3-1-5. 가장 중요한 발견: BV 절벽과 영역 규칙

모델을 다 고른 뒤 나중에 계산한 새 배치로 다시 검증했을 때, BV가 크게 틀리는 구석을 하나 발견했습니다. **바디 도즈가 0.80 미만이면서 에피 도핑이 1.40을 넘는 구석**에서 BV 예측이 실제 값과 5~13V까지 벌어졌습니다. 이 구간은 실제로 소자의 BV가 급격히 무너지는 "BV 절벽" 근처라, 완만한 함수를 가정하는 GP가 잘 맞히지 못하는 지점입니다. 그래서 이 조건(도즈 < 0.80 AND 에피 > 1.40)에 해당하면 모델이 값을 내지 않고 **거절**하도록 잠정 규칙을 넣었습니다. 이것이 앞서 말씀드린 "학습 영역 밖이면 값을 내지 않는다"는 동작의 구체적인 근거입니다.

또한 불확실도 자체도 보정했습니다. 교차검증에서 과신하는 것으로 나타난 Id와 BV 두 출력만 각각 σ에 1.70배, 1.68배를 곱해 "모른다"는 신호가 실제 오차 크기와 맞도록 조정했습니다.

### 3-1-6. 배포 검증과 한계

규격 판정 자체의 일치율도 확인했습니다. 모델 예측으로 내린 Vth 규격 판정이 실제 TCAD 값 기준 판정과 143/143건 일치했고, BV 규격 판정도 64/64건 일치했습니다. 추론 속도는 Jetson에서 1점당 0.9ms, 10만 점을 한꺼번에 돌려도 4.3초밖에 걸리지 않고, 모델 크기도 NumPy 배열만으로 0.9MB에 불과해 엣지 디바이스 배포에 문제가 없음을 확인했습니다.

진단 에이전트도 같은 철학으로 동작합니다. 서로게이트를 내부적으로 수만 번 돌려 어떤 공정 변수가 벗어났는지 확률로 추정하는데, 이때 서로게이트 자체가 "모른다"를 믿을 만하게 말할 수 있어야 진단도 "구분 불가"를 정확히 판정할 수 있습니다. 즉 서로게이트의 불확실도 신뢰성은 진단 에이전트 전체의 신뢰성을 떠받치는 바탕입니다.

다만 한계는 솔직하게 말씀드려야 합니다. 첫째, 학습·검증 데이터가 모두 TCAD **합성 데이터**이고 실제 소자와의 일치는 이번 분석에서 평가하지 않았습니다. 둘째, **BV 학습 점이 부족**합니다(188개 중 88개). 셋째, BV 절벽 규칙은 3개 샘플로 정한 **잠정 규칙**이라 더 많은 데이터로 다시 확인해야 합니다. 그래서 이 한계를 숨기지 않고, 영역 규칙과 불확실도로 "모르면 거절"하게 만든 것이 지금의 안전장치입니다. 다음 단계로는 실측 데이터와의 연결, BV 데이터 보강, 고정밀 모드의 적용 범위 확대를 계획하고 있습니다.

정리하면, AOI4184 구조를 TCAD로 재현해 데이터를 만들고, 16종의 모델을 6가지 시험으로 공정하게 비교해 2단 GP를 선정했으며, 영역 규칙과 불확실도 보정이라는 안전장치를 더해 지금의 서로게이트 모델이 완성됐습니다.

### 3-2. 전체 흐름도

저희 시스템은 4대의 장비가 역할을 나눠서 동작합니다.

- **Unity PC**: 사용자가 보는 화면입니다. 실시간 카메라 프리뷰, AOI 외관검사 요청, ML 예측/진단 요청, 검증 결과 확인, 관리자 승인까지 모두 이 화면에서 이루어집니다.
- **Jetson Orin Nano**: 엣지 디바이스입니다. 카메라 영상 캡처, AOI 외관검사, 그리고 서로게이트/진단 ML 모델을 실제로 서빙하는 ML HTTP Service(:8300)가 여기서 동작합니다.
- **Gateway 서버(WSL)**: 중앙 이벤트 접수, ROS 2 작업 배포, TCAD 워크스테이션과의 통신, 승인 처리를 담당합니다.
- **TCAD 워크스테이션(Windows, 별도 PC)**: 실제 Silvaco TCAD 정밀 시뮬레이션을 수행합니다.

여기서 한 가지 꼭 짚어야 할 구조적 특징이 있습니다. **서로게이트와 진단 모델은 Jetson 위의 ML HTTP Service에서 동작**하고, Jetson의 ROS Worker는 모델 자체가 아니라 "Gateway의 ROS 요청을 받아 로컬 ML Service를 호출하고 결과를 다시 돌려주는 어댑터"입니다. 즉 모델 추론은 항상 Jetson 안에서 로컬로 일어나고, ROS Worker는 중계 역할만 합니다.

### 3-3. 서로게이트 예측 흐름도

예측 요청이 들어왔을 때 실제로 어떤 순서로 동작하는지 보여드리겠습니다.

1. **Unity가 예측을 요청**합니다. 화면에서 공정 조건(도즈·에피·산화막)을 입력해 보냅니다.
2. **Event Gateway가 작업을 ROS로 넘깁니다.** 요청을 받으면 먼저 DB에 기록해 영속성을 확보하고, Jetson으로 작업을 전달합니다.
3. **Jetson의 Surrogate Worker가 로컬 ML Service의 `/predict`를 호출**합니다. 공정 조건을 넘기면 전기적 특성을 돌려받습니다.
4. **2단 GP가 결과를 계산**합니다. Vth, gm, Id, BV와 불확실도를 즉시 산출하고, 학습 범위 밖이면 거절 응답을 줍니다.
5. **결과가 DB에 저장되고 화면에 표시**됩니다. ROS 이벤트를 거쳐 중앙 DB(Aiven PostgreSQL)에 커밋되고, Unity 화면에 결과가 뜹니다.

### 3-4. 진단과 보정안 흐름도

예측 결과가 불량으로 나왔을 때의 흐름입니다. 참고로 진단은 예측이 끝나면 자동으로 이어지는 게 아니라, **별도의 요청으로 다시 시작**되는 독립적인 작업입니다.

1. **Unity가 진단을 요청**합니다. 측정한 Vth, gm, Id, BV 값을 화면에서 보냅니다.
2. **Gateway가 작업을 ROS로 넘깁니다.** 마찬가지로 DB에 먼저 기록한 뒤 Jetson으로 전달합니다.
3. **Jetson의 Diagnosis Worker가 ML Service의 `/diagnose`를 호출**합니다.
4. **진단 에이전트가 원인 확률과 보정안을 계산**합니다. 서로게이트 모델을 수만 번 내부적으로 돌려서 어떤 공정 변수가 벗어났는지 확률로 추정하고, 보정 조건을 제시합니다.
5. **결과가 저장되고 화면에 표시**됩니다. 원인 분석과 보정안이 DB에 기록되고 Unity 화면에 나타납니다.

이때 진단 결과가 비정상(anomaly)이고, 경로(route)가 "TCAD 재검증 필요"로 판단되고, 실제 보정 후보가 존재하는 경우에만 다음 단계인 TCAD 검증으로 넘어갑니다. 정상이면 바로 종료되고, 수동 검토가 필요한 경우엔 별도로 표시됩니다.

### 3-5. TCAD 정밀 검증 흐름도

진단 에이전트가 낸 보정안 중 확신 조건을 하나라도 충족하지 못한 것들은 TCAD 대기열에 쌓입니다. 이 대기열에 있는 후보들만 실제 TCAD로 재검증합니다.

1. **DB의 TCAD 대기열에서 후보를 꺼냅니다.**
2. **Verification Worker가 HTTP로 검증을 요청**합니다. Gateway 서버의 워커가 (물리적으로 별도의 PC인) TCAD 워크스테이션의 TCAD HTTP Service에 보정안 조건을 전송합니다.
3. **TCAD 계산 엔진이 실행**됩니다. 전달받은 조건으로 실제 Silvaco Atlas 시뮬레이션을 돌립니다. 한 점 계산에 20~30분이 걸립니다. 이 느린 계산을 꼭 필요한, 확신이 낮은 후보에만 적용함으로써 비용과 시간을 절약하는 것이 전체 아키텍처의 핵심 설계 의도입니다.
4. **결과를 DB에 저장**합니다. TCAD로 확인한 실제 전기적 특성과 규격 통과 여부를 기록합니다.
5. **Unity에 결과를 전달**합니다. 검증 결과가 화면에 표시되고, 엔지니어가 승인 여부를 판단할 수 있는 상태가 됩니다.

구조적으로 덧붙이면, Gateway 서버 PC와 TCAD 워크스테이션은 서로 다른 물리 PC이고, TCAD HTTP Service는 시뮬레이터 자체가 아니라 비동기 큐·조회 API이자 실행 래퍼입니다. 내부적으로 `dbascii.exe`라는 프로그램을 실행하고, 이 프로그램이 다시 Silvaco Atlas를 실행해서 실제 계산을 수행합니다. 계산이 오래 걸리기 때문에 Verification Worker는 요청을 보낸 뒤 완료될 때까지 주기적으로 상태를 조회(polling)하는 방식으로 동작합니다.

### 3-6. 엔지니어가 후보를 검토하는 흐름도

TCAD 검증까지 끝난 보정안이라도, **사람이 승인해야만 실제 공정에 반영**됩니다. 이것이 저희 시스템의 중요한 안전장치입니다.

1. **엔지니어가 후보를 검토**합니다. 화면에서 보정안과 TCAD 검증 결과(규격 통과 여부 포함)를 확인합니다.
2. **승인을 Gateway로 전송**합니다. 엔지니어가 승인 버튼을 누르면 그 요청이 Event Gateway로 전달됩니다.
3. **승인 명령을 DB에 기록**합니다. 누가, 언제, 어떤 보정안을 승인했는지 이력이 남습니다.
4. **승인 후 반영**됩니다. 승인된 보정안만 공정 설정값으로 전환됩니다.
5. **다음 LOT 레시피에 적용**됩니다. 단, 진행 중인 LOT은 건드리지 않고, 장비가 유휴 상태일 때 다음 LOT부터 반영합니다. 공정 중간에 변수를 바꿔서 생기는 혼란을 막기 위한 설계입니다.

### 3-7. AOI 외관 검사 흐름도

마지막으로 완성품 외관 검사, AOI입니다.

1. **IP 카메라 영상을 캡처**합니다. Jetson이 카메라 영상을 받아 링 버퍼에 계속 쌓아둡니다.
2. **미리보기 JPEG를 Unity로 전송**합니다. 현재 화면을 JPEG로 변환해 Unity에 실시간으로 보여줍니다.
3. **Unity가 AOI를 직접 요청**합니다. 여기서 중요한 구조적 차이가 있는데, 검사 버튼을 누르면 **Gateway를 거치지 않고 Unity가 Jetson에 WebSocket으로 직접 요청**합니다. 실시간성이 중요한 외관 검사이기 때문에, 중앙 Gateway를 경유하지 않는 별도의 빠른 경로를 둔 것입니다.
4. **AOI 모델이 부품과 결함을 추론**합니다. 같은 원본 프레임으로 먼저 부품(바디, 리드, 탭)을 찾고, 이어서 결함(구부러짐, 크랙, 스크래치)을 판정합니다.
5. **결과를 ROS로 중앙에 저장**합니다. 판정 결과는 ROS 이벤트를 거쳐 중앙 DB에 저장되고, 동시에 화면에도 표시됩니다.

정리하면, AOI는 실시간 응답이 핵심이라 Unity-Jetson 직접 WebSocket 경로를 쓰고, 중앙 기록을 위한 DB 저장은 그 뒤에 비동기로 따라가는 구조입니다.

## Chapter 3-1 보충. 모델 성능 지표

마지막으로 서로게이트 모델의 성능을 숫자로 말씀드리겠습니다.

- 학습 데이터는 TCAD로 생성한 합성 데이터이며, 서로게이트 1점을 계산하는 데 **0.4ms**가 걸립니다. 같은 조건을 실제 TCAD로 계산하면 20~30분이 걸리므로, 체감상 수만 배 빠른 속도입니다.
- 총 16종의 후보 모델 구조를 비교 평가했고, 최종적으로 2단 GP 구조를 선정했습니다.
- 불확실도 보정 결과, ±2σ 구간 포함률이 94~98% 수준으로 나타났습니다. 이상적인 경우(95%)에 근접한 결과로, 모델이 "확신이 낮을 때 넓게, 확신이 높을 때 좁게" 불확실도를 합리적으로 추정하고 있다는 뜻입니다.

이상으로 FabRx 시스템의 예측-진단-판단 구조와, 이를 구현하는 실제 아키텍처(서로게이트 예측, 진단/보정, TCAD 정밀 검증, 엔지니어 승인, AOI 외관검사)를 전체 흐름 중심으로 설명드렸습니다. 감사합니다.
