## Chapter 2. 프로젝트 개요 — FabRx 프로젝트 동작

안녕하십니까, 지금부터 저희가 구축한 FabRx 가상 공정 시스템을 소개하겠습니다.

저희 시스템은 세 단계로 동작합니다. **예측(Predict) → 진단(Diagnose) → 판단(Decide)** 입니다.

먼저 **예측** 단계입니다. 공정 노브 3개 — 바디 도즈, 에피 도핑, 산화막 두께 — 를 입력하면, 서로게이트 ML 모델이 즉시 Vth, gm, Id, BV를 계산해 돌려줍니다. 여기서 중요한 점은, 이 모델이 학습한 범위 밖의 입력이 들어오면 억지로 값을 내지 않고 "모른다"고 답한다는 것입니다. 잘못된 확신을 주지 않도록 설계했습니다.

다음은 **진단** 단계입니다. 예측 결과가 불량으로 판정되면, 진단 에이전트가 어떤 공정 변수가 문제인지 노브별로 확률을 추정하고 보정안을 제시합니다. 이때도 확신도가 70% 미만이면 "구분 불가"로 솔직하게 답합니다.

마지막은 **판단** 단계입니다. 진단 에이전트가 낸 보정안을 5개의 임계값 조건으로 검사합니다. 모두 통과하면 TCAD 정밀 검증을 생략할 수 있는 후보로 분류하고, 하나라도 미달이면 실제 TCAD 재검증을 요청합니다. 그리고 최종적으로 공정에 적용할지는 반드시 엔지니어가 승인합니다. AI가 모든 걸 자동으로 결정하지 않고, 사람이 마지막 의사결정을 하는 구조입니다.

## Chapter 3. 기술 아키텍처

### 3-1. 모델 사용 배경

이 예측을 담당하는 모델이 **서로게이트(Surrogate) 모델**입니다. 2단 가우시안 프로세스(2단 GP) 구조로 되어 있습니다.

입력은 노브 3개 — 바디 도즈, 에피 도핑, 산화막 두께 — 이고, 출력은 Vth, gm, Id(4V), BV 네 가지와 각각의 불확실도(σ)입니다. 실제 TCAD(Silvaco Atlas) 시뮬레이션은 한 점 계산에 20~30분이 걸리는데, 서로게이트는 이를 0.4ms 수준으로 흉내 냅니다. 목표는 "빠르고, 정확하고, 모를 때는 모른다고 말하는 모델"입니다.

이 모델이 왜 2단 GP로 결정됐는지, 그 과정을 좀 더 자세히 설명드리겠습니다. 저희는 이 모델을 **학습 데이터 생성 → EDA(탐색적 분석) → 후보 모델 비교 → 과적합·성능 분석 → 최종 선정**이라는 다섯 단계로 개발했습니다.

**첫 번째, 학습 데이터 생성입니다.** TCAD(Silvaco Athena/Atlas)로 트렌치 파워 MOSFET 구조를 직접 계산해서 데이터를 만들었습니다. 바디 도즈, 에피 도핑, 산화막 두께를 바꿔가며 총 188개 샘플을 뽑았는데, 기준값 주변 ±30% 범위에서 고르게 뽑은 "코어" 샘플 96개, 한 노브만 범위를 벗어나게 뽑은 "확장" 샘플 50개, 노브 하나만 더 넓게(±10~70%) 움직인 "단일 노브" 샘플 42개로 구성했습니다. BV(항복전압)는 계산 비용이 커서(샘플당 16~21분) 일부 98개 샘플에만 계산했습니다. 이렇게 샘플을 나눠 뽑은 이유는, 나중에 "모델이 학습한 범위를 벗어났을 때 얼마나 틀리는지"를 직접 시험해보기 위해서입니다.

**두 번째, EDA(탐색적 데이터 분석)입니다.** 데이터를 만들고 나서 바로 모델링에 들어가지 않고, 먼저 데이터의 특성을 다섯 가지 관점에서 확인했습니다.
- 양품과 불량이 적절히 섞여 있는지 확인했습니다 — Vth 규격을 벗어난 샘플이 146개 중 64개(44%)로, 원인 진단 모델을 학습시키기에 적합한 비율이었습니다.
- 어떤 공정 변수가 어떤 출력에 영향을 주는지 상관관계를 봤습니다 — Vth·gm·Id는 산화막과 바디 도즈가 주로 결정하고, BV는 에피 도핑이 거의 단독으로 결정했습니다(상관 −0.93).
- Vth, gm, Id 세 출력이 서로 얼마나 겹치는지 봤습니다 — 세 출력의 순위 상관이 매우 높아(−0.93 수준) 거의 한 몸처럼 움직인다는 걸 확인했고, 이것이 나중에 "Id를 예측할 때 Vth 예측값을 같이 넣는 2단 구조"를 쓰게 된 근거가 됐습니다.
- 입력과 출력 사이의 관계가 완만한 비선형인지 급격한 비선형인지 봤습니다 — 완만하고 약한 비선형으로 나타나, 적은 데이터로도 학습이 잘 되는 모델이 유리하다는 결론을 얻었습니다.
- 바디 도즈와 산화막이 Vth·gm에 비슷한 방향으로 영향을 줘서 서로 구분하기 어려운 구조인지도 확인했습니다.

이 다섯 가지 관찰이 바로 "어떤 모델을 후보로 삼아야 하는가"를 정하는 기준이 됐습니다.

**세 번째, 후보 모델 비교입니다.** EDA 결과를 바탕으로 총 16종의 모델을 후보로 세웠습니다. 단순한 선형·2차 모델부터, 소량 데이터에 강한 가우시안 프로세스(GP) 계열 여러 변형, 신경망 앙상블, 트리 부스팅(LightGBM), 최신 사전학습 표 데이터 모델(TabPFN), 그리고 GP와 TabPFN을 섞은 하이브리드까지 포함했습니다. 이 16종을 **같은 학습 데이터, 같은 분할 기준**으로 여섯 가지 시험을 돌렸습니다 — 교차검증(보간 정확도), 단일 노브 외삽(학습 밖 범위에서의 정확도), 방향별 외삽(한 번도 본 적 없는 방향에서의 정확도), 사후 검증(나중에 추가된 데이터로의 진짜 시험), 잡음을 입힌 학습(측정 잡음이 있을 때의 안정성), 불확실도 신뢰성(모델이 "모른다"고 말하는 게 실제로 맞는지)입니다.

**네 번째, 과적합과 성능 분석입니다.** 결과는 뚜렷했습니다. Vth·gm·Id 세 출력을 모두 목표 성능 안에 들인 모델은 7종이었고, 전부 GP 계열이었습니다. 신경망 앙상블과 트리 부스팅(LightGBM)은 학습 데이터에서는 오차가 작았지만 보지 않은 데이터에서는 오차가 25~34배까지 커지는 뚜렷한 과적합을 보였습니다. 특히 불확실도 신뢰성에서, 신경망 계열은 ±2σ 안에 실제 오차가 들어오는 비율이 15~76%에 불과해(이상적으로는 95%여야 함) "모른다고 말해야 할 때 모른다고 말하지 못하는", 즉 과신하는 모델이라는 게 드러났습니다. 반면 GP는 학습 점을 거의 완벽하게 지나가면서도(이는 잡음 없는 데이터를 정확히 보간하는 정상적인 동작입니다) 보지 않은 데이터에서의 오차가 모든 모델 중 가장 낮았고, 외삽 범위를 벗어났을 때도 가장 덜 틀렸습니다.

**다섯 번째, 최종 선정입니다.** 이 모든 분석을 종합해 최종적으로 **2단 구조를 가진 GP(2단 GP)**를 선정했습니다. 교차검증 오차가 Vth 2.19mV, gm 0.56%, Id(4V) 1.02%로 목표 성능을 크게 만족했고, BV는 0.156V로 목표(0.15V)에 근소하게 못 미쳤지만 가장 우수한 수준이었습니다. 정리하면, GP를 선택한 이유는 단순히 "정확도가 가장 높아서"가 아니라, **정확도·외삽 안정성·불확실도 신뢰성 세 가지를 모두 같은 기준으로 비교했을 때 종합적으로 가장 안정적이었기 때문**입니다. 신경망이나 트리 계열은 정확도는 비슷하게 나올 수 있어도 "모를 때 모른다고 말하는" 능력에서 신뢰할 수 없었습니다.

진단 에이전트도 같은 철학으로 만들어졌습니다. 서로게이트를 내부적으로 수만 번 돌려 어떤 공정 변수가 벗어났는지 확률로 추정하는데, 이때 서로게이트 자체가 "모른다"를 믿을 만하게 말할 수 있어야 진단도 "구분 불가"를 정확하게 판정할 수 있습니다. 즉 서로게이트의 불확실도 신뢰성은 서로게이트 자체의 정확도뿐 아니라 그 위에서 동작하는 진단 에이전트 전체의 신뢰성을 결정하는 핵심 요소였습니다.

다만 한계도 분명합니다. 학습·검증 데이터가 모두 TCAD 합성 데이터이고, 측정 잡음과 공정 산포는 가정값이며, 모델은 학습한 영역(in_domain) 안에서만 사용합니다. 실제 소자와의 일치는 이번 분석에서 평가하지 않았습니다.

### 3-2. 전체 흐름도

저희 시스템은 4대의 장비가 역할을 나눠서 동작합니다.

- **Unity PC**: 사용자가 보는 화면입니다. 실시간 카메라 프리뷰, AOI 외관검사 요청, ML 예측/진단 요청, 검증 결과 확인, 관리자 승인까지 모두 이 화면에서 이루어집니다.
- **Jetson Orin Nano**: 엣지 디바이스입니다. 카메라 영상 캡처, AOI 외관검사, 그리고 서로게이트/진단 ML 모델을 실제로 서빙하는 ML HTTP Service(:8300)가 여기서 동작합니다.
- **Gateway 서버(WSL)**: 중앙 이벤트 접수, ROS 2 작업 배포, TCAD 워크스테이션과의 통신, 승인 처리를 담당합니다.
- **TCAD 워크스테이션(Windows, 별도 PC)**: 실제 Silvaco TCAD 정밀 시뮬레이션을 수행합니다.

여기서 한 가지 꼭 짚어야 할 구조적 특징이 있습니다. **서로게이트와 진단 모델은 Jetson 위의 ML HTTP Service에서 동작**하고, Jetson의 ROS Worker는 모델 자체가 아니라 "Gateway의 ROS 요청을 받아 로컬 ML Service를 호출하고 결과를 다시 돌려주는 어댑터"입니다. 즉 모델 추론은 항상 Jetson 안에서 로컬로 일어나고, ROS Worker는 중계 역할만 합니다.

### 3-3. 서로게이트 예측 흐름도

예측 요청이 들어왔을 때 실제로 어떤 순서로 동작하는지 보여드리겠습니다.

1. **Unity가 예측을 요청**합니다. 화면에서 공정 조건(도즈·에피·산화막)을 입력해 보냅니다.
2. **Event Gateway가 작업을 ROS로 넘깁니다.** 요청을 받으면 먼저 DB에 기록해 영속성을 확보하고, Jetson으로 작업을 전달합니다.
3. **Jetson의 Surrogate Worker가 로컬 ML Service의 `/predict`를 호출**합니다. 공정 조건을 넘기면 전기적 특성을 돌려받습니다.
4. **2단 GP가 결과를 계산**합니다. Vth, gm, Id, BV와 불확실도를 즉시 산출하고, 학습 범위 밖이면 거절 응답을 줍니다.
5. **결과가 DB에 저장되고 화면에 표시**됩니다. ROS 이벤트를 거쳐 중앙 DB(Aiven PostgreSQL)에 커밋되고, Unity 화면에 결과가 뜹니다.

### 3-4. 진단과 보정안 흐름도

예측 결과가 불량으로 나왔을 때의 흐름입니다. 참고로 진단은 예측이 끝나면 자동으로 이어지는 게 아니라, **별도의 요청으로 다시 시작**되는 독립적인 작업입니다.

1. **Unity가 진단을 요청**합니다. 측정한 Vth, gm, Id, BV 값을 화면에서 보냅니다.
2. **Gateway가 작업을 ROS로 넘깁니다.** 마찬가지로 DB에 먼저 기록한 뒤 Jetson으로 전달합니다.
3. **Jetson의 Diagnosis Worker가 ML Service의 `/diagnose`를 호출**합니다.
4. **진단 에이전트가 원인 확률과 보정안을 계산**합니다. 서로게이트 모델을 수만 번 내부적으로 돌려서 어떤 공정 변수가 벗어났는지 확률로 추정하고, 보정 조건을 제시합니다.
5. **결과가 저장되고 화면에 표시**됩니다. 원인 분석과 보정안이 DB에 기록되고 Unity 화면에 나타납니다.

이때 진단 결과가 비정상(anomaly)이고, 경로(route)가 "TCAD 재검증 필요"로 판단되고, 실제 보정 후보가 존재하는 경우에만 다음 단계인 TCAD 검증으로 넘어갑니다. 정상이면 바로 종료되고, 수동 검토가 필요한 경우엔 별도로 표시됩니다.

### 3-5. TCAD 정밀 검증 흐름도

진단 에이전트가 낸 보정안 중 확신 조건을 하나라도 충족하지 못한 것들은 TCAD 대기열에 쌓입니다. 이 대기열에 있는 후보들만 실제 TCAD로 재검증합니다.

1. **DB의 TCAD 대기열에서 후보를 꺼냅니다.**
2. **Verification Worker가 HTTP로 검증을 요청**합니다. Gateway 서버의 워커가 (물리적으로 별도의 PC인) TCAD 워크스테이션의 TCAD HTTP Service에 보정안 조건을 전송합니다.
3. **TCAD 계산 엔진이 실행**됩니다. 전달받은 조건으로 실제 Silvaco Atlas 시뮬레이션을 돌립니다. 한 점 계산에 20~30분이 걸립니다. 이 느린 계산을 꼭 필요한, 확신이 낮은 후보에만 적용함으로써 비용과 시간을 절약하는 것이 전체 아키텍처의 핵심 설계 의도입니다.
4. **결과를 DB에 저장**합니다. TCAD로 확인한 실제 전기적 특성과 규격 통과 여부를 기록합니다.
5. **Unity에 결과를 전달**합니다. 검증 결과가 화면에 표시되고, 엔지니어가 승인 여부를 판단할 수 있는 상태가 됩니다.

구조적으로 덧붙이면, Gateway 서버 PC와 TCAD 워크스테이션은 서로 다른 물리 PC이고, TCAD HTTP Service는 시뮬레이터 자체가 아니라 비동기 큐·조회 API이자 실행 래퍼입니다. 내부적으로 `dbascii.exe`라는 프로그램을 실행하고, 이 프로그램이 다시 Silvaco Atlas를 실행해서 실제 계산을 수행합니다. 계산이 오래 걸리기 때문에 Verification Worker는 요청을 보낸 뒤 완료될 때까지 주기적으로 상태를 조회(polling)하는 방식으로 동작합니다.

### 3-6. 엔지니어가 후보를 검토하는 흐름도

TCAD 검증까지 끝난 보정안이라도, **사람이 승인해야만 실제 공정에 반영**됩니다. 이것이 저희 시스템의 중요한 안전장치입니다.

1. **엔지니어가 후보를 검토**합니다. 화면에서 보정안과 TCAD 검증 결과(규격 통과 여부 포함)를 확인합니다.
2. **승인을 Gateway로 전송**합니다. 엔지니어가 승인 버튼을 누르면 그 요청이 Event Gateway로 전달됩니다.
3. **승인 명령을 DB에 기록**합니다. 누가, 언제, 어떤 보정안을 승인했는지 이력이 남습니다.
4. **승인 후 반영**됩니다. 승인된 보정안만 공정 설정값으로 전환됩니다.
5. **다음 LOT 레시피에 적용**됩니다. 단, 진행 중인 LOT은 건드리지 않고, 장비가 유휴 상태일 때 다음 LOT부터 반영합니다. 공정 중간에 변수를 바꿔서 생기는 혼란을 막기 위한 설계입니다.

### 3-7. AOI 외관 검사 흐름도

마지막으로 완성품 외관 검사, AOI입니다.

1. **IP 카메라 영상을 캡처**합니다. Jetson이 카메라 영상을 받아 링 버퍼에 계속 쌓아둡니다.
2. **미리보기 JPEG를 Unity로 전송**합니다. 현재 화면을 JPEG로 변환해 Unity에 실시간으로 보여줍니다.
3. **Unity가 AOI를 직접 요청**합니다. 여기서 중요한 구조적 차이가 있는데, 검사 버튼을 누르면 **Gateway를 거치지 않고 Unity가 Jetson에 WebSocket으로 직접 요청**합니다. 실시간성이 중요한 외관 검사이기 때문에, 중앙 Gateway를 경유하지 않는 별도의 빠른 경로를 둔 것입니다.
4. **AOI 모델이 부품과 결함을 추론**합니다. 같은 원본 프레임으로 먼저 부품(바디, 리드, 탭)을 찾고, 이어서 결함(구부러짐, 크랙, 스크래치)을 판정합니다.
5. **결과를 ROS로 중앙에 저장**합니다. 판정 결과는 ROS 이벤트를 거쳐 중앙 DB에 저장되고, 동시에 화면에도 표시됩니다.

정리하면, AOI는 실시간 응답이 핵심이라 Unity-Jetson 직접 WebSocket 경로를 쓰고, 중앙 기록을 위한 DB 저장은 그 뒤에 비동기로 따라가는 구조입니다.

## Chapter 3-1 보충. 모델 성능 지표

마지막으로 서로게이트 모델의 성능을 숫자로 말씀드리겠습니다.

- 학습 데이터는 TCAD로 생성한 합성 데이터이며, 서로게이트 1점을 계산하는 데 **0.4ms**가 걸립니다. 같은 조건을 실제 TCAD로 계산하면 20~30분이 걸리므로, 체감상 수만 배 빠른 속도입니다.
- 총 16종의 후보 모델 구조를 비교 평가했고, 최종적으로 2단 GP 구조를 선정했습니다.
- 불확실도 보정 결과, ±2σ 구간 포함률이 94~98% 수준으로 나타났습니다. 이상적인 경우(95%)에 근접한 결과로, 모델이 "확신이 낮을 때 넓게, 확신이 높을 때 좁게" 불확실도를 합리적으로 추정하고 있다는 뜻입니다.

이상으로 FabRx 시스템의 예측-진단-판단 구조와, 이를 구현하는 실제 아키텍처(서로게이트 예측, 진단/보정, TCAD 정밀 검증, 엔지니어 승인, AOI 외관검사)를 전체 흐름 중심으로 설명드렸습니다. 감사합니다.
